description: 맡은 기능의 정책을 위키에서 읽고 슬라이스로 나눠 서버 이슈를 쓰고 올린다
---

맡은 기능(예: UPL) 하나의 이슈를 만드는 절차다(이슈는 역할 라벨 `server`, `client`로 구분한다). 슬라이스를 진행하는 것은 `/next`와 `/work`다. 기능 ID는 `$ARGUMENTS`로 받는다.

1. 기능 ID가 없으면 묻는다. 위키 저장소는 `docs/policy/*.md`의 `위키:` 줄에서 찾고, 없으면 `soohy00/ttadak-wiki`(정책은 `docs/policy/`)를 쓴다.
2. 위키의 정책 파일 목록을 읽어 그 기능 ID가 적힌 파일을 찾는다(`gh api repos/<위키>/contents/<정책 폴더>`). 찾지 못하면 멈추고 묻는다.
3. `python3 scripts/policy_check.py --table <위키> <파일>`로 정책 표를 만든다. 정책을 **확정, 검토 중, 미결정**으로 나눈다.
4. `python3 scripts/policy_check.py --coverage <위키> <파일>`로 이미 이슈가 있는 정책을 찾는다. 이슈가 없는 **확정** 정책만 이슈로 만들 대상이다. 이미 이슈가 있는 정책으로 이슈를 또 만들지 않는다.
5. 대상 정책을 슬라이스로 나눈다. 슬라이스 하나는 한 사람이 PR 하나로 끝낼 수 있고 사용자에게 의미가 있는 최소 단위다. 서로 의존하는 정책(예: 검사한 뒤에 추출한다)은 앞의 슬라이스를 먼저 만들고 `의존:`으로 잇는다. 분할 이유를 한 줄씩 쓴다.
6. 이슈의 본문은 저장소의 이슈 템플릿(`.github/ISSUE_TEMPLATE/` 폴더)의 형식으로 쓴다. `git fetch` 뒤 `git show origin/main:.github/ISSUE_TEMPLATE/task.md`로 읽는다. 실패하면 템플릿이 병합되기 전이므로 `git show origin/setting/github-templates:.github/ISSUE_TEMPLATE/task.md`로 읽는다. 머리의 설정(`---` 사이)과 주석은 본문에 넣지 않는다.
   - 제목: `종류: 한국어 요약`(예: `feat: 자료를 올린다`). 종류는 템플릿의 안내에서 고른다. 역할은 제목에 넣지 않는다.
   - "개요": 무엇을 왜 하는지 한두 줄
   - "작업 내용": 해야 할 일의 체크박스
   - "완료 조건": 끝났을 때 확인할 수 있는 결과. 정책의 값은 옮겨 쓰지 않고 정책 번호로 가리킨다.
   - "참고": 첫 두 줄은 `기획: <위키 저장소> <파일> <정책 번호>`(예: `UPL-01~04`)와 `의존: #번호`다. 해당이 없으면 `없음`을 쓴다. 두 줄은 줄의 맨 앞에서 시작하고 값은 같은 줄에 쓴다. 이유: `next.py`와 `policy_check.py`가 이 두 줄을 읽는다.
   - 요구와 정책의 내용은 본문에 쓰지 않는다. 정책은 위키가 말한다.
7. 분할안(제목, 정책 번호, 의존, 이유)을 사용자에게 먼저 한 번에 보인다. 사용자가 고치라고 하면 고친다.
8. 선행 이슈부터 `gh issue create --title "<제목>" --body-file <본문 파일> --label server --label "<종류의 라벨>" --assignee @me`로 올린다. 본문 파일은 `_workspace/issue-<영문-요약>.md`다. 종류의 라벨은 제목의 종류와 같은 것이다(`💫 feat`, `🐛 fix`, `🔧 chore`, `📝 docs`, `🔨 refactor`, `✅ test`, `🎨 style`, `⚡ perf`, `👷 ci`, `📦 build`, `⏪ revert`). 담당자는 올리는 사용자다(맡은 기능이기 때문이다). 의존에 쓸 번호는 앞 이슈가 올라간 뒤의 번호를 쓴다. 올릴 때마다 권한 확인이 뜨는데 그것이 마지막 확인이다. 거절되면 그 이슈와 그에 의존하는 이슈를 올리지 않고 멈춘다.
9. 다 올린 뒤 `python3 scripts/policy_check.py --coverage <위키> <파일>`를 다시 돌려 이슈가 없는 확정 정책이 없는지 확인하고 결과를 알린다.
10. 확정이 아닌 정책(검토 중, 미결정)은 이슈로 만들지 않고 번호와 상태를 목록으로 알린다. PM에게 물어야 하면 `work` 스킬의 질문 절차(`.claude/skills/work/references/policy.md`)를 따른다(질문의 초안은 사용자가 승인한다).

## 하지 않는 일

- 확정이 아닌 정책으로 이슈를 만들지 않는다. 이유: 위키가 정하지 않은 것을 서버가 구현하게 된다.
- 이슈를 고치거나 닫지 않는다. 이유: 이미 올라간 이슈는 다른 사람이 보고 있다.
- `client` 이슈를 쓰지 않는다. 이유: 클라이언트의 이슈는 클라이언트가 쓴다.
- 위키를 고치지 않는다.
- 사용자가 맡지 않은 기능의 이슈를 만들지 않는다.
