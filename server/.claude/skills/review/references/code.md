# code — 코드 점검

구현이 끝나고 `check.sh`가 통과한 뒤에 변경을 `code-reviewer`로 점검한다. 성능, 코드 품질, 보안을 본다. 정책의 정확성과 정책대로의 구현은 `doc-reviewer`의 몫이다.

## 절차

1. `git diff <base>...HEAD -- . ':(exclude)docs/review'`를 `_workspace/diff-NN.patch`에 저장한다. 리뷰 문서는 뺀다. 이유: 리뷰 문서에는 `doc-reviewer`의 리포트가 있다(ADR-0001의 18번). diff로 넘기면 훅이 막는 읽기를 돌아가게 된다.
2. `code-reviewer`를 부른다. 입력은 diff의 경로, plan의 경로, 읽을 ADR의 경로(`0003`, `0006`), 라운드 번호다. r2면 그 리뷰어의 r1 리포트(`_workspace/review-NN-code-reviewer.md`)의 경로도 넘긴다. `doc-reviewer`의 리포트는 넘기지 않는다.
3. 리포트를 `work/references/shared/리뷰-결과-합치기.md`로 합쳐서 `docs/review/`에 기록한다.

## 점검하는 것

- **코드 품질**: TDA(다른 객체의 상태를 꺼내 밖에서 판단하지 않고 그 객체에게 시킨다), 의존성(ADR-0003의 방향과 컨텍스트 사이의 `api`), 네이밍(용어 표의 말), 가독성, 중복, 책임 분배(규칙이 도메인 객체에 있는가). ADR의 "리뷰"가 지키는 요구가 기준이다.
- **성능**: N+1, 반복문 안의 조회, 트랜잭션 안의 외부 호출. 실제 느린지는 측정이 필요해서 판정하지 않는다.
- **보안**: OWASP Top 10의 항목을 이 diff에 대어 본다. 다른 사용자의 자원이면 404로 존재를 숨기는지, 토큰과 비밀 값이 로그와 응답에 나가는지, 입력의 검증이 있는지를 특히 본다.
