# conformance — 정책과 코드의 대조

문서의 요구(spec의 AC, domain의 R, ADR의 MUST와 MUST NOT) 하나하나가 코드와 테스트에서 어떻게 되어 있는지 네 가지로 나눈다. `doc-reviewer`가 슬라이스를 닫을 때 한 번 한다(ADR-0001의 13번). 어긋남이 남아 있으면 닫지 못한다.

## 네 가지

| 분류 | 뜻 | 행동 |
|---|---|---|
| 지키고 테스트가 강제한다 | 코드가 지키고, 어기면 테스트나 검사가 깨진다 | 없음 |
| 지키지만 강제가 없다 | 코드는 지키는데 어기는 변경을 막는 테스트나 검사가 없다 | 테스트나 검사를 더할 후보로 일지의 "관찰"에 적는다 |
| 어긋난다 | 코드가 요구를 어긴다 | 코드를 고친다. 문서가 틀렸을 수 있으면 사용자에게 올린다 |
| 아직 없다 | 요구가 가리키는 코드가 아직 없다 | plan의 범위 밖이면 그대로 둔다. 범위 안이면 어긋남이다 |

## 절차

1. 대조할 문서를 정한다. 이 슬라이스의 plan이 가리키는 spec, domain의 요구와, 구현이 따른 ADR(`0003`, `0006`)의 요구다.
2. `doc-reviewer`를 부른다. 절차는 `conformance`, 입력은 plan의 경로, diff의 경로, 그 문서들의 경로다. diff는 이때 `code.md`의 1번과 같이 리뷰 문서를 빼고 다시 만든다. 이유: 검증 뒤의 변경이 빠지지 않게 하고, `code-reviewer`의 리포트가 섞이지 않게 한다. 요구마다 분류와 근거(코드의 위치, 테스트 이름)를 돌려준다.
3. 리포트를 `work/references/shared/리뷰-결과-합치기.md`로 합쳐서 `docs/review/`에 기록한다.
4. "어긋난다"가 있으면 `implement`로 돌아간다. "지키지만 강제가 없다"는 일지의 "관찰"에 적는다. 같은 것이 두 번 나오면 `reflect`가 검사로 올리자고 제안한다.

## 하지 않는 일

- 도구가 이미 강제하는 요구(ArchUnit, 포매터)를 요구마다 분류하지 않는다. "지키고 테스트가 강제한다"로 한 줄로 묶는다. 이유: 읽는 양을 줄인다.
