# docs — 정책과 문서 점검

domain, spec, ADR, plan을 쓴 직후 승인 전에 `doc-reviewer`로 점검한다. 정책이 정확한지, 빠진 것이 없는지, 문서를 잘 썼는지 본다. 이유: 승인은 사용자의 일이라서, 사용자가 승인하기 전에 모순과 빈틈을 먼저 걸러 둔다.

## 절차

1. 점검할 문서의 경로를 정한다. `git status`로 바뀐 `docs/` 파일을 확인한다.
2. `doc-reviewer`를 부른다. 절차는 `docs`, 입력은 문서의 경로, `docs/README.md`, `.claude/skills/work/references/doc-style.md`, 정책 기록(`docs/policy/`)과 해당 일지의 경로, 관련 domain·spec·ADR의 경로다.
3. 리포트를 `work/references/shared/리뷰-결과-합치기.md`로 합쳐서 `docs/review/`에 기록한다.

## 점검하는 것

- **정확성**: 위키의 정책(정책 기록)과 일지의 "결정 (사용자)"와 문서가 다르지 않은가. 확정이 아닌 정책을 근거로 쓰거나 위키에 없는 제품 결정을 AI가 채우지 않았는가. 문서끼리 모순이 없는가. AI의 제안이 사용자의 결정처럼 쓰이지 않았는가.
- **완결성**: 문서가 다루는 상황에서 이어지는 빠진 경우가 없는가. 예외 경로, 경계값, 상태 전이, 권한, 오류, 정하지 않은 채 쓴 숫자. 빠진 경우는 "정해지지 않았다"는 질문으로 올린다.
- **작성 품질**: README의 규칙을 지켰는가. 흐린 말, 한 문장에 요구 하나, 용어 표의 말, ID, 출처의 구분. 기계가 잡는 것(상태의 줄, 수준과 키워드)은 `docs-lint`가 이미 본다.
