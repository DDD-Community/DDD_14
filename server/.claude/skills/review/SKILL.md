# review

쓴 사람이 자기 것을 점검하지 않게 한다. 점검은 두 리뷰어 에이전트가 하고, 이 스킬은 어떤 절차로 부르고 결과를 어떻게 남기는지 정한다. 이유: 쓴 쪽은 자기 것의 약점을 못 본다(ADR-0001의 구성 요소 표).

## 리뷰어

| 리뷰어 | 보는 것 | 절차 |
|---|---|---|
| `doc-reviewer` | 정책이 정확한가, 빠진 것이 없는가, 문서를 잘 썼는가. 정책이 코드로 구현됐는가 | docs, conformance |
| `code-reviewer` | 성능, 코드 품질(TDA, 의존성, 네이밍, 가독성), 보안(OWASP Top 10) | code |

## 라우팅

| 요청 | 절차 | 파일 |
|---|---|---|
| 문서를 점검한다(domain, spec, ADR, plan) | docs | `references/docs.md` |
| 정책이 코드와 테스트에 구현됐는지 대조한다 | conformance | `references/conformance.md` |
| 코드 변경을 점검한다 | code | `references/code.md` |

지금 절차의 파일만 읽는다. 요청이 둘 이상이면 앞 절차부터 하나씩 한다.

## 공통 규칙

- 리뷰어는 읽기만 한다. 위반 목록만 돌려주고 파일을 고치지 않는다(ADR-0001의 9번). 이유: 고치는 사람과 점검하는 사람이 같아지면 독립 검증이 사라진다.
- 두 리뷰어는 서로의 리포트를 읽지 않는다(ADR-0001의 18번). 이유: 한쪽이 다른 쪽을 따라가면 독립 검증이 사라진다. 합치는 것은 호출한 쪽이다.
- 에이전트에게는 파일 경로를 준다. 내용을 붙여 넣지 않는다. 이유: 입력이 갈라지지 않고 토큰이 준다.
- 리뷰는 Claude 모델의 리뷰어로만 한다. 코드를 다른 모델의 서비스에 보내지 않는다(ADR-0001의 16번, 17번). 이유: 사용자가 정했다. 코드와 비밀 값이 외부 서비스로 나가는 것을 막는다.
- **결과는 `docs/review/`에 기록한다**(ADR-0001의 31번, 32번). 지적마다 받아들였는지, 받아들이지 않았는지, 이유, 결정한 사람을 남긴다. 절차는 `work/references/shared/리뷰-결과-합치기.md`다.
- 지적은 사실로만 한다. 근거(문서의 줄, 코드의 위치)가 없는 지적은 `확인 필요`에 둔다.
