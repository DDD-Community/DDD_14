# explain-diff

AI가 쓴 코드를 사용자가 이해한 채로 병합하게 한다. 이 단계는 승인이 아니라 **사용자가 코드를 이해하려는 것**이다. 이유: 이해하지 못한 코드를 병합하면 다음 슬라이스에서 사용자가 고칠 수 없다. 손을 덜 타려는 목표와 부딪치므로 슬라이스를 닫을 때 한 번만 한다.

## 절차

1. 변경을 본다(`git diff <base>...HEAD`). 문서의 변경과 코드의 변경을 나눈다.
2. 변경을 한 이야기로 해설한다. 파일 순서가 아니라 요청의 흐름 순서(표현 계층 → 응용 계층 → 도메인 객체 → 저장)로 말한다. 각 부분에서 "왜 여기에 있는가"를 ADR이나 AC로 가리킨다.
3. 사용자가 이 슬라이스에서 놓치기 쉬운 곳을 먼저 말한다: AI가 정한 것("결정 (AI)"), 규칙이 놓인 곳(도메인 객체), 동시성이나 트랜잭션의 경계.
4. 퀴즈를 세 개까지 낸다. 코드를 보지 않고 답할 수 있는 질문으로 쓴다. 예: "20MB를 넘는 파일을 올리면 누가 거절하나?" 답이 틀리면 해당 부분을 다시 해설한다.
5. 사용자가 "이해했다"고 하면 끝낸다. 해설과 퀴즈의 결과는 일지의 "관찰"에 한 줄만 쓴다. 해설 문서를 따로 남길지는 정하지 않았다(ADR-0001의 정하지 않은 것 5번). 그때까지 대화에만 둔다.

## 하지 않는 일

- 해설하다가 코드나 문서를 고치지 않는다. 문제를 찾았으면 사용자에게 알리고 `implement`나 `document`로 돌아간다.
- 퀴즈의 정답을 사용자가 말하기 전에 보여 주지 않는다.
