# work

슬라이스 하나(기능 하나, 브랜치 하나, PR 하나)를 문서가 기준이 되도록 진행한다. **너(메인 세션)가 오케스트레이터이고 구현도 한다.** 테스트 작성과 점검은 에이전트(`test-author`, `doc-reviewer`, `code-reviewer`)와 도구가 맡고, 사람은 결정과 승인(문서, plan, 병합)에만 손을 쓴다(ADR-0001).

이 파일은 라우터다. 단계의 절차는 `references/<단계>.md`, 단계가 같이 쓰는 것은 `references/shared/`에 있다. 지금 단계의 파일만 읽는다. 이유: 읽는 양(토큰)을 줄이려고 나눴다.

## 단계와 라우트

| 단계 | 하는 일 | 파일 | 사람이 손을 쓰는 곳 |
|---|---|---|---|
| 1. 정책 읽기 | 위키의 정책을 읽고 정책 기록과 질문을 만든다 | `references/policy.md` | 질문의 승인(답은 PM) |
| 2. 문서 | domain, spec, ADR을 쓰고 점검한다 | `references/document.md` | **승인** |
| 3. 계획 | plan을 쓴다 | `references/plan.md` | **승인** |
| 4. 테스트 | `test-author`가 구현을 보지 않고 테스트를 쓴다 | `references/test.md` | |
| 5. 구현 | 테스트를 통과시키는 코드를 쓴다 | `references/implement.md` | |
| 6. 검증 | 기계와 `code-reviewer`가 점검한다 | `references/verify.md` | |
| 7. 이해 (선택) | 사용자가 원하면 `explain-diff` 스킬로 변경을 해설한다 | (스킬 `explain-diff`) | 퀴즈에 답한다 |
| 8. 종료 | 일지, 수정의 줄, 커밋, push, PR | `references/close.md` | **병합** |

요청이 둘 이상의 단계에 걸리면 앞 단계부터 하나씩 한다. 한 번에 여러 단계의 파일을 읽지 않는다.

## 시작할 때

1. `python3 scripts/status.py`를 실행해 지금 단계를 계산한다(스킬 `status`와 같다). 상태는 저장하지 않고 문서와 git에서 계산한다(ADR-0001의 10번).
2. 결과를 한 줄로 사용자에게 알리고 그 단계의 라우트 파일로 간다.
3. 계산 결과가 서로 어긋나면(예: plan이 승인인데 테스트가 없음) 고르지 않고 사용자에게 묻는다.

## 새 슬라이스를 시작할 때

슬라이스는 이슈 하나에서 시작한다. 이슈는 `/issues <기능ID>`가 위키의 정책을 읽어 만든다. `/next`(`.claude/commands/next.md`)가 시작할 수 있는 이슈를 보이고, 사용자가 고른 이슈의 브랜치를 `scripts/start-slice.sh`로 만든다. 브랜치 이름은 `<종류>/<이슈번호>-<영문-요약>`이고 종류는 커밋 종류와 같다(예: `feat/3-family-members`, ADR-0005의 3번). 이슈는 서버가 위키의 정책 번호를 근거로 쓴다.

- 이슈는 포인터다. 요구와 정책을 이슈 본문에서 읽지 않고 문서에서 읽는다. 이슈와 문서가 다르면 문서가 맞다.
- 정책 기록과 plan의 상태의 줄 아래에 `- 이슈: #번호`를 쓴다.
- 종료 단계에서 PR의 설명에 `Closes #번호`를 쓰고, 슬라이스를 닫은 뒤에는 `python3 scripts/next.py`로 다음 후보를 사용자에게 알린다. 시작은 사용자가 정한다.
- 이슈에서 시작하지 않은 작업은 `<종류>/<영문-요약>` 브랜치에서 한다. 종류는 커밋 종류와 같다(예: 문서면 `docs/branch-kinds`, 하네스와 설정이면 `setting/next-command`).

## 관문

앞 단계를 통과하지 못하면 다음 단계로 넘어가지 않는다. 이 표는 상태 그래프이고, 훅이 막을 수 있는 것은 훅이 막는다.

| 넘어가려면 | 확인 | 이유 |
|---|---|---|
| 정책 읽기 → 문서 | 정책 기록이 있고, 구현 대상이 위키 상태 확정인 정책뿐이다 | 위키가 정하지 않은 것을 서버가 정하지 않는다 |
| 문서 → 계획 | 쓴 문서의 상태가 `승인`이다 | 의도(spec)는 사람의 일이다 |
| 계획 → 테스트 | plan의 상태가 `승인`이다 | 이 승인 뒤에는 슬라이스 안에서 AI가 알아서 진행한다 |
| 테스트 → 구현 | 새 테스트가 실행해서 red다(`test-author`의 노트) | 통과하는 테스트는 아무것도 확인하지 않는다 |
| 구현 → 검증 | 요청 범위의 테스트가 green이다 | |
| 검증 → 종료 | `scripts/check.sh` 통과, `code-reviewer`의 차단이 0건이다 | 도구가 최종 판정이다. 에이전트의 PASS는 `check.sh`를 대신하지 않는다 |
| 검증 → 구현 | 위가 실패했다 | 실패하면 종료로 갈 수 없다 |
| 이해 (선택) | 사용자가 `explain-diff`를 요청했다 | 요청이 없으면 이 단계를 건너뛰고 종료로 간다. 이해는 사용자가 정한다 |

검증을 건너뛰고 종료할 수 없다(ADR-0001의 2번). 구현 중의 승인된 spec 편집은 훅(`.claude/hooks/guard-edit.sh`)이 막는다. 승인된 plan 없이 `src/main`을 고치면 훅은 막지 않고 알린다(슬라이스 밖의 수정이 있기 때문이다). plan 승인 뒤에 구현하는 것은 이 스킬이 지킨다.

## 코드가 옳을 때 (spec이 틀렸을 때)

코드와 spec이 다르면 코드를 고친다(README의 "기준"). 사용자가 코드가 옳다고 판단하면 아래 순서로 간다(ADR-0001의 24~26번).

1. 사용자의 말을 일지의 "결정 (사용자)"에 적는다.
2. plan의 상태를 `승인`에서 `제안`으로 되돌린다. 이유: `guard-edit` 훅은 승인된 plan이 있는 동안 승인된 spec의 편집을 막는다. spec이 바뀌면 plan이 낡았을 수 있기도 하다.
3. spec을 먼저 고치고 "수정" 줄(일지 스텝, 확인이 필요하다)을 단다. 코드는 그다음이다.
4. 고친 spec과 plan에서 바뀐 곳을 사용자에게 보이고 plan의 승인을 다시 받는다. 승인 전에는 `src/main`을 고치지 않는다(훅이 막는다).

사용자가 말하지 않았는데 plan의 상태를 되돌리지 않는다. 이유: 훅은 plan의 상태 줄만 보고 사용자의 말을 모르므로, 이 길을 AI가 막는 훅을 피하는 데 쓸 수 있다.

## 위키가 바뀌었을 때

세션을 시작할 때 `python3 scripts/policy_check.py`가 위키의 변경을 알려 준다(`status`가 실행을 안내한다).

1. 바뀐 정책 번호와 그 정책을 근거로 쓰는 AC가 출력된다. 사용자에게 그대로 보인다.
2. 순서는 정책 기록, spec, 코드다(README의 "정책"). 정책 기록의 표와 해시를 먼저 고치고, 그다음 spec의 AC를 고치고 승인을 다시 받는다. 코드는 그다음이다.
3. 구현 중이면 "코드가 옳을 때"와 같이 plan의 상태를 `승인`에서 `제안`으로 되돌려야 spec을 고칠 수 있다. 사용자의 말이 있을 때만 되돌린다.
4. 정책이 확정에서 검토 중으로 바뀌었으면 그 AC의 구현을 멈추고 사용자에게 올린다.

## 슬라이스 밖의 수정

슬라이스 없이 `src/main`을 고칠 때(작은 수정, 병합 뒤의 수정)는 ADR-0001의 27~28번을 따른다.

1. 고치기 전에 이 수정이 닿는 AC와 R을 찾는다(`@Covers`로 찾는다).
2. 수정이 spec의 요구와 다르면 고치기 전에 사용자에게 올린다. 위 "코드가 옳을 때"로 간다.
3. 수정이 테스트의 기대값을 바꾸면(동작이 달라지면) 사용자에게 올린다. 기대값을 맞춰 테스트를 고치지 않는다.
4. 고친 뒤 영향받는 테스트를 실행해 통과를 확인하고, 끝에 `scripts/check.sh`를 돌린다.

## 중간 산출물과 다시 시작

에이전트의 결과와 diff는 `_workspace/<run-id>/`에 파일로 둔다(ADR-0001의 21~23번). `<run-id>`는 `NN-<대상>-<순번>`이다(예: `02-code-1`).

| 파일 | 누가 쓰나 | 내용 |
|---|---|---|
| `00_diff.patch` | 메인 세션 | 첫 줄 `# commit: <해시>`, 그 아래 `git diff` |
| `10_<에이전트>_report.md` | 메인 세션 | 리뷰어의 최종 응답 전문. 받자마자 고치지 않고 저장한다 |
| `20_test-author_note.md` | `test-author` | 테스트 노트 |

- 에이전트를 부르기 전에 같은 run-id의 파일이 있는지 본다. 있고 `00_diff.patch`의 해시가 현재 `HEAD`와 같으면 다시 부르지 않고 그 파일을 읽는다. 해시가 다르면 낡은 것이므로 새 순번으로 만든다.
- 세션이 다시 시작되면 `python3 scripts/status.py`가 `docs/review/`에 아직 옮기지 않은 리포트와 낡은 diff를 알려 준다. 알려 준 리포트부터 `shared/리뷰-결과-합치기.md`로 옮긴다.
- `_workspace/`는 git에 올리지 않는다. 기록으로 남길 것(리뷰와 처리)은 `docs/review/`가 맡는다.

## 공통 규칙

- 사람이 정하거나 승인해야 하는 지점은 `references/shared/사람-확인-지점.md`가 정본이다. 이유: 외부에 보이는 행동은 되돌리기 어렵다.
- 스텝(한 번의 작업 단위)이 끝나면 일지를 쓴다. 형식은 `references/shared/일지-쓰는-법.md`다. 이유: 결정의 출처를 잊지 않으려는 것이다.
- 문서가 정하지 않은 것을 네가 정했으면 일지의 "결정 (AI)"에 적고, 문서에는 "확인이 필요하다"를 붙인다(ADR-0001의 5번). 사용자가 결정할 일을 스스로 정하지 않는다. 이유: 지어낸 이유가 승인을 통과하는 것을 막는다.
- 사용자에게 한 번에 묻는 질문은 세 개까지다(`AGENTS.md`).
- 승인된 spec이 코드와 다르면 코드를 고친다. spec을 코드에 맞춰 고치지 않는다. 코드가 옳다고 판단해도 사용자에게 올리고, 사용자가 정한 뒤에 spec을 먼저 고친다(README의 "기준").
- 같은 실패는 **2회 재시도 후 중단**하고 미해결 항목을 보고한다. 이유: 기준을 낮춰 통과시키는 것을 막는다.
- 에이전트는 서브에이전트 방식으로 한 번에 하나씩 부르고, 결과를 최종 응답으로 받는다(ADR-0001의 19번과 20번). 이유: 에이전트끼리 말하지 않아야 두 리뷰어가 서로의 리포트를 읽지 않는다.
- 에이전트에게는 파일 경로를 주고 내용을 붙여 넣지 않는다. 이유: 입력이 갈라지지 않고 토큰이 준다.
- 에이전트의 결과(리포트)가 없으면 1회 다시 부르고, 또 없으면 중단해 보고한다. 이유: 빈 결과로 다음 단계로 넘어가지 않는다.
- 읽는 문서는 plan 작업의 ID(`AC-1.2`, `R-1.1`)가 가리키는 줄과 ADR의 해당 요구로 좁힌다(ADR-0001의 7번). 문서 전체를 읽지 않는다.
- 어느 ADR을 읽는지는 각 라우트 파일에 있다. 코드는 ADR-0003, 0006, 테스트는 ADR-0004를 읽는다.
- 리뷰 리포트는 전문을 사용자에게 보인다. 경로만 알리지 않는다.

## 스킬을 나눌 신호

아래 중 하나라도 생기면 스킬을 나눈다.

- 한 라우트가 다른 라우트의 내용을 길게 설명한다.
- 이 파일이 150줄을 넘는다.
- 라우트가 열 개를 넘는다.
