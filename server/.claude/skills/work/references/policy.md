# policy — 정책 읽기

슬라이스의 이슈가 가리키는 위키의 정책을 읽고, 무엇을 이번에 구현하고 무엇을 PM에게 물을지 나눈다. 제품의 결정은 위키(PM)가 한다. 이 단계에서 AI는 정책을 옮기고 구멍을 찾을 뿐 새 정책을 만들지 않는다. 끝나면 `document`로 간다.

## 읽는 것

- `docs/README.md`의 "정책"과 "문서의 지도"(정책 기록의 위치와 수명).
- 이슈 본문의 `기획:` 줄(위키의 파일과 정책 번호).
- 같은 기능의 기존 정책 기록(`docs/policy/`)과 `docs/journal/`의 내 일지의 마지막 스텝의 "남은 일".

## 절차

1. 이슈 본문에서 위키 저장소, 파일, 정책 번호를 찾는다. 없으면 이슈를 쓴 사람에게 묻는다(스스로 위키에서 고르지 않는다).
2. 위키의 최신 커밋 해시를 읽고(`gh api repos/<위키>/commits/HEAD --jq .sha`), 그 해시의 정책 표를 만든다: `python3 scripts/policy_check.py --table <위키> <파일> <해시>`. 해시는 기록에 고정한다. 이유: 위키는 계속 바뀌므로 어느 버전을 읽고 썼는지 남겨야 한다.
3. `docs/policy/<기능ID>.md`를 쓴다. 첫 항목은 상태의 줄(`- 상태: 제안 (AI가 제안)`)이고, 그 아래에 `- 위키:`, `- 파일:`, `- 해시:` 줄을 쓴다. 이슈가 있으면 `- 이슈: #번호`도 쓴다. 표의 "이 슬라이스" 열에 "예"를 쓸 정책은 위키 상태가 확정인 것뿐이다.
4. 확정이 아닌 정책(검토 중, 미결정)과 위키가 정하지 않았는데 서버가 정해야 하는 것(숫자, 오류 문구, 예외)을 기획 질문 표(`# | 질문 | 정책 | 상태`)에 모은다. 상태는 "열림"이다. 질문은 AI가 정해서 쓰지 않고 "무엇이 정해지지 않았는가"만 쓴다.
5. 질문 초안을 사용자에게 보이고 승인을 받는다. 승인되면 사용자가 위키 저장소의 이슈로 올린다(`gh issue create -R <위키>`는 권한 확인이 뜬다). 올린 이슈의 주소를 질문 표에 적는다. PM의 답이 오면 상태를 "닫힘"으로 바꾸고 위키가 바뀐 해시로 기록을 갱신한다(기록의 해시와 표를 바꾸고 일지에 쓴다).
6. 확정 정책이 하나도 없으면 이 슬라이스는 시작할 수 없다. 사용자에게 알리고 다른 이슈를 고르게 한다(`/next`).
7. 사용자에게 "읽은 결과가 맞을까요?"를 묻고, 맞으면 `document`로 간다. 스텝이 끝나면 일지를 쓴다(`shared/일지-쓰는-법.md`).

## 하지 않는 일

- 위키의 정책을 고치거나 해석해서 채우지 않는다. 바꿀 것은 질문이다.
- 검토 중이거나 미결정인 정책을 구현 대상에 넣지 않는다. 사용자가 PM과 합의했다고 말해도 위키가 확정이 될 때까지 기다리는 것이 기본이다. 예외는 사용자가 일지의 "결정 (사용자)"에 적은 경우다.
- 위키에 없는 제품의 결정(숫자, 문구)을 "합리적인 값"으로 채우지 않는다.
- 코드와 ADR의 결정(스택, 구조)을 이 단계에서 정하지 않는다.
