# plan — 계획

승인된 문서에서 슬라이스를 만들 작업의 순서와 "검증할 내용"을 쓰고 사용자의 승인을 받는다. 이 승인이 끝나면 슬라이스 안의 일은 AI가 알아서 진행한다(ADR-0001의 3번).

## 읽는 것

- 슬라이스가 다루는 spec의 AC, domain의 R. 문서 전체가 아니라 plan에 넣을 ID의 줄이다.
- 관련 ADR의 요구: 구조는 `0003`, 테스트는 `0004`.

## 절차

1. 작업을 쪼갠다. 작업 하나는 한두 개의 AC나 R을 다룰 크기로 한다. 이유: red를 작은 범위로 확인하고 green이 되면 바로 닫으려는 것이다.
2. `docs/plan/NN-<슬라이스>.md`를 쓴다. 첫 항목은 상태의 줄이다. 아래 양식을 따른다.
3. 작업마다 그 작업이 다루는 ID를 적는다(README의 "ID"). ID가 없는 작업은 두지 않는다.
4. "검증할 내용"에는 사용자가 확인할 수 있는 말로 무엇이 되면 끝인지 쓴다. 코드와 ERD는 plan에 넣지 않는다.
5. `python3 scripts/trace_check.py --plan`으로 작업마다 ID가 있는지, 모든 AC와 R이 어떤 작업에 속하는지 확인한다. 통과하면 `doc-reviewer`로 점검한다(`review` 스킬의 docs 절차).
6. 사용자에게 승인을 묻는다(`document.md`의 "승인"과 같다). 승인되면 상태의 줄을 `승인 (사용자가 결정, <날짜> 일지 스텝 N)`으로 바꾼다.
7. 일지를 쓰고 커밋한 뒤(`shared/커밋과-PR.md`) `test`로 간다.

## plan의 양식

```markdown
# 슬라이스 NN. <이름>

- 상태: 제안 (AI가 제안)

범위: 이 슬라이스가 만드는 것과 만들지 않는 것.

| 작업 | 다루는 ID | 검증할 내용 | 상태 |
|---|---|---|---|
| 1. ... | AC-1.1, R-1.1 | 사용자가 확인할 수 있는 말 | 대기 |
```

작업의 상태는 `대기`, `진행`, `완료`다. `완료`는 `check.sh`가 통과한 뒤에만 쓴다.

## 하지 않는 일

- 승인되지 않은 plan으로 `test`나 `implement`로 가지 않는다. 훅은 승인된 plan 없이 `src/main`을 고치면 알리기만 하므로(슬라이스 밖의 수정 때문이다) 이 규칙은 이 스킬이 지킨다.
- plan에 없는 AC나 R을 슬라이스 중간에 몰래 더하지 않는다. 필요하면 plan을 고치고 다시 승인받는다.
