# 사람 확인 지점

사람이 정하거나 승인해야 넘어가는 지점의 정본이다. 라우트 파일은 여기를 가리키기만 한다. 사용자가 손을 쓰는 곳은 정책 기록의 컨펌, 문서의 승인, plan의 승인, PR의 병합이다. 퀴즈(`explain-diff`)는 사용자가 원할 때만 한다(ADR-0001의 3번).

| 지점 | 누가 | 이유 |
|---|---|---|
| 목표와 범위, 범위를 넓히는 결정 | 사용자 | AI가 범위를 넓히면 합의 없이 일이 커진다 |
| 이슈의 분할안과 올리기 | AI가 쓰고 올린다. 올릴 때 권한 확인이 마지막 확인이다 | 이슈 쓰기는 서버의 일이고 AI가 맡았다. 되돌리기 어려운 것은 올리는 순간뿐이라 그 순간에 확인한다 |
| 기획 질문의 초안 | 사용자(그 기능의 담당자)가 승인한다. 올리는 것은 AI이고, 올릴 때의 권한 확인이 마지막 확인이다 | AI가 PM에게 보내는 말을 사람이 확인한다 |
| 기획 질문의 답, 정책의 확정 | PM | 제품의 결정은 위키가 한다. AI와 서버는 정하지 않는다 |
| 정책 기록의 컨펌("읽은 결과가 맞을까요?", 컨펌의 말은 문서의 승인과 같다) | 사용자 | 잘못 읽은 정책 위에 domain과 spec을 쓰지 않는다 |
| 문서(domain, spec, ADR)의 승인 ("승인", "진행해", "ㄱㄱ", "그래") | 사용자 | 승인 전에는 계획으로 가지 않는다 |
| plan의 승인 | 사용자 | 이 승인 뒤에는 슬라이스 안에서 AI가 알아서 진행한다 |
| 이미 있는 요구를 바꾸는 것 | 사용자 | AI는 코드에 맞춰 spec을 고치지 않는다 |
| `FAIL` 판정(문서와 코드가 다름), 재시도 2회 후 미해결 | 사용자 | 기준을 AI가 낮춰 통과시키지 않는다 |
| 커밋, push, PR 만들기 | AI. 커밋은 묻지 않는다. push와 PR 만들기는 권한 확인이 마지막 확인이다 | 하네스의 규칙이다(ADR-0001). 같은 일을 두 번 확인하지 않는다 |
| PR 병합 | 작성자 외 서버 팀원 한 명의 승인과 CI 통과를 받은 뒤 사람이 한다. CI가 생기기 전에는 CI 대신 PR에 `check.sh` 통과를 적는다. API 계약을 바꾼 PR은 클라이언트의 승인도 받는다(위치와 방법은 4차 회의에서 정한다) | 작성자가 혼자 병합하지 않는다(ADR-0001의 3번). AI는 병합하지 않는다 |
| 배포 | 사람만 | |

`main`과 `develop`에 직접 push하는 것과 force push는 누구도 하지 않는다.

## 스테이징과 비밀 값

- 경로를 지정해서 스테이징한다. `git add -A`와 `git add .`는 쓰지 않는다. 이유: 의도하지 않은 파일(비밀 값, 산출물)이 섞이는 것을 막는다.
- `.env`와 `.env.*`(`.env.example`은 예외)는 스테이징하지 않는다.
- 커밋 전에 `git status`로 위 파일이 없는지 본다.

## 권한 설계 이유

`.claude/settings.json`의 권한은 세 종류로 나눈다.

- `allow`: 읽기와 조회, 컴파일과 테스트 명령, `git add`와 `git commit`. 커밋은 훅(`journal-check`)이 일지, `-A`와 `-a`, 비밀 파일을 확인하므로 권한 확인을 띄우지 않는다. `git push`는 넣지 않아서 실행마다 권한 확인이 뜬다.
- `ask`: `gh pr create`처럼 외부에 보이는 행동.
- `deny`: `.env` 읽기, `rm -rf`, `main`과 `develop` push, force push, `gh pr merge`. 되돌리기 어렵거나 사람만 해야 하는 행동이다.
