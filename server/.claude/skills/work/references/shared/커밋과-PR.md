# 커밋과 PR

커밋과 push와 PR의 절차다. 브랜치 전략은 `main`과 기능 브랜치만 두는 것이다(ADR-0005). PR은 squash merge한다(ADR-0005). 브랜치, 커밋, PR의 공통 규칙은 저장소의 Git Workflow Rule(client/docs/rules/git-workflow)이다(ADR-0005).

## 커밋

스텝이 끝날 때마다 아래 절차로 커밋한다. 커밋할지 사용자에게 묻지 않는다. 승인 전의 정책 기록, 문서, plan도 상태가 `제안`인 채로 커밋하고, 승인되면 상태의 줄을 바꿔 다시 커밋한다. 이유: 승인 여부는 상태의 줄이 말한다. 커밋을 미루면 변경이 일지 없이 작업 트리에 남는다(2026-11-24 일지 스텝 1). 잘게 나뉜 커밋은 첫 push 전에 정리한다(아래 "커밋의 정리").

1. `git status`로 바뀐 파일을 본다. `.env`와 `_workspace/`가 없는지 확인한다.
2. 경로를 지정해서 올린다(`git add <경로>`). 이유: `git add -A`는 의도하지 않은 파일을 섞는다.
3. 코드를 바꾸는 커밋에는 그 스텝의 일지(`docs/journal/`)가 함께 있어야 한다. 이유: 기록 없는 변경을 막는다. `journal-check.sh`가 커밋 전에 확인한다.
4. 메시지는 `종류: 한국어 요약`이고, 범위가 필요하면 `종류(범위): 한국어 요약`이다. 종류는 `feat`, `fix`, `chore`, `docs`, `refactor`, `test`, `style`, `perf`, `ci`, `build`, `revert` 중 하나다. 슬라이스의 커밋은 끝에 이슈 번호를 단다. 예: `feat: 자료를 올린다 (#3)`.
5. 테스트와 그 테스트를 통과시키는 구현은 같은 커밋에 넣는다. 이유: 실패하는 테스트를 공유 브랜치에 남기지 않으려는 것이다(ADR-0004의 F4.2).
6. 커밋한 뒤 push하기 전에 `./scripts/check.sh`를 통과시킨다. 실패하면 고쳐서 새 커밋을 만들고 다시 돌린다. push 전의 로컬 커밋이라 괜찮다. 이유: `check.sh`는 작업 트리가 깨끗할 때만 통과 기록을 남기고, `pre-push-check`는 push하는 커밋의 기록만 본다.

## 커밋의 정리

첫 push 전에 슬라이스의 커밋을 PR 리뷰의 단위로 다시 나눈다. 나눈 커밋은 리뷰를 위한 것이라, squash merge로 `main`에는 하나로 합쳐져도 나눈다. 이유: 스텝마다 한 커밋은 고치고 되돌린 흔적까지 섞여서 리뷰어가 커밋을 하나씩 따라 읽기 어렵다.

1. 브랜치를 이미 push했으면(`git log -1 --oneline origin/<브랜치>`가 커밋을 보이면) 나누지 않는다. `git log`는 권한 확인 없이 돈다. 이유: 나눈 커밋을 올리려면 force push가 필요한데, force push는 하지 않는다.
2. 단위는 정책 기록, 문서(domain, spec, ADR), plan, plan의 작업마다 테스트와 구현(위 5번), 리뷰 문서다. 메시지는 위 4번의 형식이다.
3. 지금 커밋의 해시를 적어 두고, 전체 일지를 `_workspace/journal-full.md`에 복사한 뒤 `git reset $(git merge-base HEAD origin/main)`로 커밋을 푼다. 변경은 작업 트리에 그대로 남는다.
4. 단위마다 경로를 지정해서 스테이징하고 커밋한다. 일지는 쌓기만 하므로, 커밋마다 그 단위까지의 스텝만 남긴 일지의 앞부분을 함께 넣는다(`journal-check`가 커밋마다 일지를 요구한다). 마지막 커밋에서 일지를 전체로 되돌린다.
5. `git diff <3번의 해시> HEAD`가 비어 있는지 확인한다. 이유: 나누는 중에 빠지거나 바뀐 변경이 없어야 한다.
6. 나눈 커밋으로 `./scripts/check.sh`를 다시 돌린다. 커밋 해시가 바뀌어서 전의 통과 기록은 쓰지 못한다.

## push와 PR

1. 원격 저장소는 팀의 저장소다. 원격이 없는 환경이면 커밋까지만 하고 사용자에게 알린다.
2. 브랜치 이름의 종류는 `feat`, `fix`, `chore`, `docs`, `refactor`, `test` 중 하나다. 슬라이스는 `<종류>/<이슈번호>-<영문-요약>`(예: `feat/3-family-members`), 이슈가 없는 작업은 `<종류>/<영문-요약>`(예: `docs/branch-kinds`)이다. 기능 브랜치는 `main`에서 만든다. `main`에 직접 push하지 않는다. force push를 하지 않는다.
3. PR의 설명은 클라이언트와 함께 쓰는 PR 템플릿(저장소 루트의 `.github/` 폴더)의 형식으로 `_workspace/pr-<영문-요약>.md`에 쓴다. `git fetch` 뒤 `git show origin/main:.github/pull_request_template.md`로 최신 템플릿을 읽는다. 읽은 템플릿에 "체크리스트" 절이 없으면 새 템플릿이 병합되기 전이므로 `git show origin/setting/github-templates:.github/pull_request_template.md`로 읽는다. 템플릿 파일은 고치지 않는다. 이유: `gh pr create`에 본문을 직접 주면 GitHub가 템플릿을 채우지 않는다.
4. 템플릿의 절은 아래처럼 채운다. 템플릿의 절이 바뀌었으면 템플릿을 따른다.
   - "관련 이슈": 슬라이스면 `Closes #번호`를 쓴다. 이유: 병합하면 이슈가 닫히고 `scripts/next.py`가 다음 후보를 계산한다. 이슈가 없으면 "없음"을 쓴다.
   - "변경 사항": 슬라이스의 이름, 한 일, plan의 경로, 바꾼 spec과 ADR, 다룬 AC와 R
   - "변경 이유 / 접근 방식": 이유와 이 슬라이스 일지의 "결정 (AI)" 목록
   - "테스트": 실행한 명령과 결과(`./scripts/check.sh`). 하지 않은 검증은 체크하지 않는다.
   - "스크린샷 / 결과": API를 바꿨으면 요청과 응답의 예. 해당이 없으면 "해당 없음"
   - "리뷰어에게": 볼 커밋의 순서, 중점적으로 볼 곳, 사용자가 확인할 것, 알려진 한계
   - "하네스 피드백": 헤맨 곳과 이번에 더하거나 고친 규칙과 검사. 없으면 "없음"
   - "체크리스트": 직접 확인한 항목만 체크한다. 🖱️ 항목은 AI가 절대 체크하지 않는다. 이유: PR을 올리는 사람이 코드의 흐름을 이해했는지 스스로 표시하는 칸이다.
5. 묻지 않고 `gh pr create --base main --title "<제목>" --body-file <그 파일> --assignee @me --label server --label "<종류의 라벨>"`로 PR을 만든다. 제목은 커밋 메시지의 형식(위 "커밋"의 4번)으로 쓴다. 이유: squash merge의 커밋 제목이 된다. 종류의 라벨은 제목의 종류와 같은 것이다: `💫 feat`, `🐛 fix`, `🔧 chore`, `📝 docs`, `🔨 refactor`, `✅ test`, `🎨 style`, `⚡ perf`, `👷 ci`, `📦 build`, `⏪ revert`. 리뷰어는 사용자가 알려 준 사람을 `--reviewer`로 지정한다. 알려 준 사람이 없으면 지정하지 않고, PR을 만든 뒤 사용자에게 지정해 달라고 알린다. 외부에 보이는 행동이라 권한 확인이 뜨고, 그 권한 확인이 PR의 마지막 확인이다. 설명을 따로 확인받지 않는다. 이유: 같은 일을 두 번 확인하지 않는다(2026-11-24 일지 스텝 28). PR의 설명은 병합 전에 PR에서 고칠 수 있다.
6. 병합하지 않는다. 사용자에게 PR의 주소를 알린다. 병합의 조건은 `사람-확인-지점.md`의 "PR 병합"이다.
