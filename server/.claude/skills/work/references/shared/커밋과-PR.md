# 커밋과 PR

커밋과 push와 PR의 절차다. 브랜치와 커밋의 규칙은 4차 회의(11/24) 뒤에 ADR-0005에서 정한다. 아래는 임시 절차이고, 규칙이 정해지면 맞춰 고친다.

## 커밋

정책 기록, 문서(domain, spec, ADR), plan은 사용자가 컨펌한 뒤에 커밋한다. 컨펌 전에는 상태가 `제안`인 채로 작업 트리에 둔다. 컨펌되면 상태의 줄을 바꾸고, 일지를 쓰고, 아래 절차로 커밋한 뒤 다음 단계로 간다. 이유: 컨펌받지 않은 문서가 이력에 남지 않게 하고, 단계마다 돌아갈 지점을 만든다.

1. `git status`로 바뀐 파일을 본다. `.env`와 `_workspace/`가 없는지 확인한다.
2. 경로를 지정해서 올린다(`git add <경로>`). 이유: `git add -A`는 의도하지 않은 파일을 섞는다.
3. 코드를 바꾸는 커밋에는 그 스텝의 일지(`docs/journal/`)가 함께 있어야 한다. 이유: 기록 없는 변경을 막는다. `journal-check.sh`가 커밋 전에 확인한다.
4. 메시지는 한국어로 `종류: 요약`이다. 종류는 `test`, `file`, `docs`, `chore`, `setting`, `feat`, `refactor`, `fix` 중 하나다(임시). 슬라이스의 커밋은 끝에 이슈 번호를 단다. 예: `feat: 자료를 올린다 (#3)`.
5. 테스트와 그 테스트를 통과시키는 구현은 같은 커밋에 넣는다. 이유: 실패하는 테스트를 공유 브랜치에 남기지 않으려는 것이다(ADR-0004의 F4.2).
6. 커밋한 뒤 push하기 전에 `./scripts/check.sh`를 통과시킨다. 실패하면 고쳐서 새 커밋을 만들고 다시 돌린다. push 전의 로컬 커밋이라 괜찮다. 이유: `check.sh`는 작업 트리가 깨끗할 때만 통과 기록을 남기고, `pre-push-check`는 push하는 커밋의 기록만 본다.

## push와 PR

1. 원격 저장소는 팀의 저장소다. 원격이 없는 환경이면 커밋까지만 하고 사용자에게 알린다.
2. 브랜치 이름의 종류는 커밋 종류와 같다. 슬라이스는 `<종류>/<이슈번호>-<영문-요약>`(예: `feat/3-family-members`), 이슈가 없는 작업은 `<종류>/<영문-요약>`(예: `docs/branch-kinds`)이다. `main`과 `develop`에 직접 push하지 않는다. force push를 하지 않는다.
3. PR의 설명을 `Closes #번호`, 한 일, 결정 (AI), 리뷰어가 볼 곳 순서로(PR 템플릿은 팀과 정하는 중이라 없다. 정해지면 그 형식을 따른다) `_workspace/pr-<영문-요약>.md`에 쓰고 경로를 알려 사용자가 확인하게 한다. 사용자가 본 뒤에 `gh pr create`로 PR을 만든다. 대상은 `develop`이다. 외부에 보이는 행동이라 권한 확인이 뜬다. 이유: PR의 설명은 사용자가 병합을 정하는 근거이고, 한 번 올리면 알림이 가고 되돌리기 어렵다.
4. 슬라이스의 PR 설명 첫 줄에 `Closes #번호`를 쓴다. 이유: 병합하면 이슈가 닫히고 `scripts/next.py`가 다음 후보를 계산한다.
5. PR의 설명에 담을 것: 슬라이스의 이름, plan의 경로, 다룬 AC와 R, 이 슬라이스 일지의 "결정 (AI)" 목록, 사용자가 확인할 것.
6. 병합하지 않는다. 사용자에게 PR의 주소를 알린다. 병합의 조건은 `사람-확인-지점.md`의 "PR 병합"이다.
