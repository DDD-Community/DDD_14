# implement — 구현

테스트를 통과시키는 코드를 쓴다. 문서가 비워 둔 곳은 네가 정하고 기록한다. 코드가 문서와 다르면 코드를 고친다.

## 읽는 것

- plan의 그 작업, 그 작업의 AC·R, 그 작업이 쓰는 ADR의 요구.
- 코드를 쓰면 `0003`(아키텍처), `0006`(코드 컨벤션), `0002`(스택).
- 기준 코드가 있으면(예: `BaseEntity`, 응답 DTO의 예) 그것을 따른다(ADR-0001의 15번).

## 절차

1. 가장 작은 테스트부터 통과시킨다. 한 번에 한 작업만 한다.
2. 테스트를 실행해 green을 확인한다(`./gradlew test --tests <대상>`).
3. 문서가 정하지 않은 것을 구현이 정해야 하면 두 곳에 적는다. 일지의 "결정 (AI)"에 적고, 해당 문서에 그 결론과 "확인이 필요하다"를 적는다(ADR-0001의 5번). 이미 있는 요구를 바꾸는 것은 하지 않는다. 사용자에게 올린다.
4. 작업이 끝나면 plan의 작업을 `완료`로 바꾸지 않는다. `verify`가 통과한 뒤에만 바꾼다.
5. 요청 범위의 테스트가 모두 green이면 `verify`로 간다. 스텝이 끝나면 일지를 쓴다.

## 하지 않는 일

- 승인된 spec이나 domain을 고치지 않는다. 구현이 옳아 보여도 사용자에게 올린다(`guard-edit.sh` 훅이 spec 편집을 막는다). 사용자가 코드가 옳다고 정하면 `work`의 "코드가 옳을 때" 순서로 간다. 이유: 코드에 맞춰 문서를 고치면 문서가 기준이 아니게 된다.
- 테스트를 약하게 만들거나 `@Disabled`를 붙여 통과시키지 않는다(ADR-0004의 F1, F2).
- 겪지 않은 문제를 풀려고 구조나 추상화를 만들지 않는다(ADR-0003의 15번).
