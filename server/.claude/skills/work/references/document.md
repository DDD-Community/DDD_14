# document — 문서 쓰기

정책 기록의 확정된 정책을 domain, spec, ADR로 옮겨 쓰고 점검하고 사용자의 승인을 받는다. 승인된 문서가 `plan`의 입력이다. 의도(spec)는 사람의 일이라서 이 단계의 승인은 사용자만 한다.

## 읽는 것

- `references/doc-style.md`(요구의 수준, 문장)와 `docs/README.md`의 "ID", "상태의 줄".
- 정책 기록(`docs/policy/`)의 확정된 정책과 닫힌 질문. spec의 AC마다 근거(정책 번호나 "기술 결정")를 쓴다.
- spec을 쓰면 해당 컨텍스트의 domain의 용어 표.
- ADR을 쓰면 관련 spec과 기존 ADR의 해당 절.

## 절차

1. **domain부터 쓴다** (`docs/domain/NN-<컨텍스트>.md`). 용어 표(한글, 영어 이름)와 항상 참인 규칙(`R-<번호>.<번호>`)을 쓴다. 이유: spec이 쓸 말이 먼저 정해져야 한다.
2. **spec을 쓴다** (`docs/spec/NN-<기능>.md`). 시스템이 무엇을 하는지와 API의 모양을 쓴다. 수용 기준마다 `AC-<spec 번호>.<번호>`를 붙인다. 어떻게 만드는지(클래스, 테이블, 처리의 순서)는 쓰지 않는다.
3. **ADR이 필요하면 쓴다** (`docs/adr/NNNN-<결정>.md`). 데이터 모델, 공개 API의 계약, 보안은 구현 전에 spec이나 ADR에서 정한다(ADR-0003의 뺀 규칙 43번이 README의 "문서가 먼저"로 남았다).
4. ADR의 요구는 `- (번호) 문장 [지키는 것]` 목록으로, spec의 AC와 domain의 R은 `ID | 수준 | 기준` 표로 쓴다. 문장은 `doc-style.md`의 키워드와 문장 규칙을 따른다. 규칙 위반은 `docs-lint` 훅이 쓰는 즉시 알려 준다.
5. 문서마다 첫 항목에 `- 상태: 제안 (AI가 제안)`을 쓴다.
6. **`doc-reviewer`로 점검한다.** `review` 스킬의 docs 절차를 따른다. 결과는 `shared/리뷰-결과-합치기.md`로 합치고 `docs/review/`에 기록한다.
7. 사용자에게 승인을 묻는다. 아래 "승인"을 따른다.
8. 승인되면 상태의 줄을 `승인 (사용자가 결정, <날짜> 일지 스텝 N)`으로 바꾼다. 일지를 쓰고 커밋한 뒤(`shared/커밋과-PR.md`) `plan`으로 간다.

## 승인

0. 승인을 묻기 전에 승인할 문서의 경로와 이번에 바뀐 곳을 사용자에게 보인다. 사용자는 IDE나 GitHub에서 문서를 연다. 사용자가 문서를 열어 본 것을 승인으로 치지 않는다.
1. 먼저 "이 문서를 이 내용으로 승인할까요?"라고 명시적으로 묻는다. 열린 질문이나 "결정 (AI)"에 답이 없는 것이 있으면 묻지 않고 답을 먼저 받는다.
2. 바로 다음 사용자 답이 "승인", "진행해", "ㄱㄱ"이면 승인이다. "ㅇㅇ"처럼 질문에 대한 단순 응답으로도 나오는 말은 승인으로 치지 않는다. 불분명하면 다시 묻는다.
3. 승인 뒤 문서를 고치면 상태의 줄에 수정의 줄을 더하고, AI가 고쳤으면 "확인이 필요하다"를 적는다.

이유: 승인은 계획과 구현을 시작하는 관문이라 우연한 말로 통과하지 않게 한다.

## 하지 않는 일

- 사용자가 정하지 않은 권장(SHOULD)과 허용(MAY)을 새로 만들지 않는다.
- 일지의 과정(누가 무엇을 물었는가)을 문서에 쓰지 않는다. 일지의 날짜와 스텝 번호로 가리킨다.
- 손으로 쓴 API 문서를 만들지 않는다. API의 모양은 spec에만 있다.
