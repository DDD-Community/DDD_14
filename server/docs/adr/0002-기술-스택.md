# ADR-0002. 기술 스택

- 상태: 제안 (AI가 제안. 팀의 승인 전이다)

읽는 법은 `.claude/skills/work/references/doc-style.md`를 따른다. 굵은 키워드가 없는 문장은 설명이다.

## 맥락

서버는 Java와 Spring Boot로 만든다(서버 팀이 정했다). Java 25를 쓰는 것, Gradle과 Lombok을 쓰는 것, 로컬 개발과 로컬 테스트가 H2와 `ddl-auto=update`를 쓰는 것, CI가 운영 DB와 같은 종류의 DB를 쓰는 것은 사용자가 정했다. 나머지는 AI의 제안이다. 운영 DB의 종류와 AI 모델은 4차 회의(11/24)에서 정한다(위키 `product/overview`의 "아직 정하지 않은 것"). 그래서 DB를 가정하는 5, 6, 7, 15번은 MySQL을 가정한 제안이고, 회의에서 바뀌면 고친다. 코드가 아직 없다. 프로젝트를 만들 때 4.0이나 4.1 중 어느 줄을 쓸지 정하고, 그 줄의 최신 패치를 쓴다. 이 ADR을 쓴 2026-11-23에 공개된 Spring Boot의 최신은 4.0.10과 4.1.3이다(2026-11-20 출시).

| 용어 | 뜻 |
|---|---|
| 마이그레이션 | 스키마의 변경을 순서대로 적은 SQL 파일. Flyway가 적용한다 |
| 운영 DB | 서비스가 쓰는 DB. 4차 회의에서 정한다. 아래는 MySQL을 가정한다 |

## 결정

요구마다 끝의 대괄호에 지키는 것을 적는다. `[리뷰]`는 검사로 만들지 못한 요구이고 코드 리뷰가 확인한다.

### 언어와 프레임워크

- (1) 서버는 Java 25와 Spring Boot 4.0.10 이상을 **반드시** 써야 한다. 4.1을 쓰면 4.1.3 이상이다. JDK는 25.0.5.1 이상이다. Spring Boot의 이 버전 아래에는 Spring Security의 원격 코드 실행 취약점(CVE-2026-59273)이 있고, JDK 25.0.5.1 아래에는 2026-11-17에 공개된 보안 수정이 빠져 있다. [빌드 설정]
- (2) 빌드는 Gradle을 **반드시** 써야 한다. [빌드 설정]
- (3) 서버는 Lombok을 **반드시** 써야 한다. ADR-0006와 ADR-0003의 응답 DTO가 `@Builder`를 쓰기 때문이다. [빌드 설정]

### 저장

- (4) 영속성은 Spring Data JPA를 **반드시** 써야 한다. [빌드 설정]
- (5) 운영 DB는 MySQL을 **반드시** 써야 한다. [빌드 설정]
- (6) CI와 운영의 스키마 변경은 Flyway 마이그레이션으로만 **반드시** 해야 한다. [설정 값을 확인하는 테스트 (아래 7번)]
- (7) JPA의 스키마 검증(`ddl-auto=validate`)을 CI와 운영에서 **반드시** 켜야 한다. 엔티티와 마이그레이션이 어긋나면 시작하지 못한다. [설정 값을 확인하는 테스트]

로컬은 H2와 `ddl-auto=update`로 빠르게 개발한다. CI는 운영과 같은 종류의 DB를 Testcontainers로 띄우고, 마이그레이션이 만든 스키마를 `validate`로 검증한다. 마이그레이션 파일을 빼먹고 커밋하면 CI가 막는다.

### 보안

- (8) 인증과 인가는 Spring Security를 **반드시** 써야 한다. 로그인 방식과 토큰은 정하지 않았다(위키 ACC-03이 미결정). [빌드 설정]
- (9) 입력 검증은 Bean Validation(`spring-boot-starter-validation`)을 **반드시** 써야 한다. [빌드 설정]

### 테스트

- (10) 테스트는 JUnit 5와 AssertJ를 **반드시** 써야 한다. [빌드 설정]
- (11) 구조 검사는 ArchUnit을 **반드시** 써야 한다. ADR-0003의 의존 방향과 ADR-0006의 엔티티 규칙을 검사한다. [빌드 설정]

### 코드 형식

- (12) 코드의 형식 검사와 정리는 Spotless를 **반드시** 써야 한다. 규칙은 `.editorconfig`(4칸 공백, 120자)를 따른다. [빌드 설정과 CI]

### 로컬과 CI의 DB

- (13) 로컬 개발은 스키마를 `ddl-auto=update`로 만들 **수 있다**. [리뷰]
- (14) 로컬 개발과 로컬 테스트는 H2를 쓸 **수 있다**. [리뷰]
- (15) CI의 통합 테스트는 운영 DB와 같은 종류의 DB를 Testcontainers로 **반드시** 써야 한다. [빌드 설정과 CI]

## 버린 대안

| 대안 | 좋은 점 | 버린 이유 |
|---|---|---|
| 로컬에서 docker compose로 운영 DB를 띄운다 | 로컬이 운영과 같은 DB다 | 사용자가 로컬은 H2로 충분하다고 정했다. 운영 DB와의 차이는 CI가 잡는다 |
| Kotlin, 다른 프레임워크 | | 서버 팀이 Java와 Spring Boot를 정했다 |

## 결과

- Spring Boot 4는 3.x와 달라진 점이 많다(Hibernate, Jackson, Spring Security의 주 버전이 오른다). 이 하네스와 ADR의 예시는 3.x의 지식으로 쓰였을 수 있어서, 첫 코드를 쓸 때 맞는지 확인한다.
- 로컬 테스트는 H2로 빠르다. 대신 H2와 운영 DB의 차이(SQL 문법, 잠금)로 로컬에서 통과한 테스트가 CI에서 실패할 수 있다. 잠금과 동시성의 테스트는 CI에서만 믿을 수 있다.
- 운영 DB가 4차 회의에서 MySQL이 아니게 되면 5, 6, 7, 15번과 "버린 대안"을 고친다.
- 외부 시스템(AI 모델, 소셜 로그인)은 테스트에서 fake로 대체한다(ADR-0004의 E1.1).
