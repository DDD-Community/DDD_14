# ADR-0005. 커밋과 브랜치

- 상태: 제안 (보류. 브랜치 전략, 커밋 종류와 형식, 병합 방식은 4차 회의(11/24)에서 팀 전체가 정한다)

읽는 법은 `.claude/skills/work/references/doc-style.md`를 따른다. 굵은 키워드가 없는 문장은 설명이다.

## 맥락

모노레포라서 서버와 클라이언트가 같은 저장소를 쓴다. 클라이언트는 `main` 기준의 짧은 브랜치, Conventional Commits, squash 병합을 이미 쓴다. 서버가 같은 규칙을 따를지, 따로 정할지는 팀이 정한다. 이 ADR은 정하기 전이라 결정을 쓰지 않는다.

하네스의 일부는 임시로 아래를 가정한다. 4차 회의에서 정한 뒤에 맞춰 고친다.

| 가정하는 곳 | 가정 |
|---|---|
| `scripts/start-slice.sh`, `.claude/skills/work/references/shared/커밋과-PR.md` | `develop`에서 `<종류>/<이슈번호>-<영문-요약>` 브랜치를 만들고, 종류는 여덟 가지(test, file, docs, chore, setting, feat, refactor, fix)다 |
| `.claude/settings.json`, `.claude/hooks/pre-push-check.sh` | `main`과 `develop`에 직접 push하지 않는다 |
| `scripts/status.py` | 브랜치 이름의 `종류/<이슈번호>-...`에서 이슈 번호를 읽는다 |
| (CI 워크플로는 아직 없다) | 초기 셋팅 때 `server/**`가 바뀐 PR에서 `check.sh`를 도는 워크플로를 만든다. 보관한 초안은 `main`에 push나 PR이 올 때 도는 것을 가정한다 |

| 1 | 브랜치 전략(`main` 기준 짧은 브랜치인가, gitflow인가) | 4차 회의(11/24) |
| 2 | 브랜치 이름과 커밋 메시지의 형식과 종류 | 4차 회의(11/24) |

| 4 | 코드 리뷰의 방식 | 4차 회의(11/24) |
| 5 | 이슈의 형식과 담당자 규칙 | 4차 회의 뒤 |
