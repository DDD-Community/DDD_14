# ADR-0001. 하네스

- 상태: 제안 (AI가 제안. 팀의 승인 전이다)

읽는 법은 `.claude/skills/work/references/doc-style.md`를 따른다. 굵은 키워드가 없는 문장은 설명이다.

## 맥락

사용자가 하네스의 목표를 둘로 정했다. 사용자의 손을 덜 타는 것(사용자는 결정과 승인에만 손을 쓴다)과 문서가 낡지 않는 것이다. 토비의 방식(문서가 먼저이고, 스펙이 기준이며, 같은 교정이 두 번 나오면 규칙이나 검사로 올린다)과 우아콘의 방식(메인 세션과 스킬을 중심에 두고 에이전트를 줄이며, 단계를 훅으로 강제한다)을 따랐다.

사용자가 정한 것: 두 목표, 리뷰는 Claude 모델만 쓴다(다른 모델의 교차 리뷰는 두지 않는다), 하네스를 첫 슬라이스 전에 먼저 만든다, 스킬 다섯 개, 에이전트에 `test-author`와 코드 리뷰를 둔다, 커밋과 push와 PR은 AI가 하고 병합은 사용자가 한다. 나머지(훅, 스크립트, 흐름의 단계 이름, 읽는 범위)는 AI의 제안이다.

| 용어 | 뜻 |
|---|---|
| 하네스 | AI가 일하는 방식을 고정하는 장치 전체. 지침(`AGENTS.md`), 스킬, 에이전트, 훅, 검사 스크립트다 |
| 스킬 | AI가 필요할 때 읽는 절차 문서(`.claude/skills/`) |
| 에이전트 | 독립된 맥락에서 일하는 보조 AI(`.claude/agents/`) |
| 훅 | 도구를 쓰는 때 자동으로 도는 검사(`.claude/hooks/`). 토큰을 쓰지 않는다 |
| 오케스트레이터 | 슬라이스의 단계를 정하고 순서를 지키게 하는 것. 이 프로젝트에서는 `work` 스킬을 따르는 메인 세션이다 |
| 슬라이스 | 사용자에게 가치가 있는 최소 기능 하나. 첫 슬라이스는 위키의 확정 정책(예: UPL)에서 `/issues`가 정한다 |

## 결정

요구마다 끝의 대괄호에 지키는 것을 적는다. `[리뷰]`는 검사로 만들지 못한 요구이고 코드 리뷰가 확인한다.

### 슬라이스의 흐름

슬라이스 하나는 아래 여덟 단계를 지난다. 굵게 쓴 단계가 사용자가 손을 쓰는 곳이다.

| 단계 | 하는 일 | 누가 |
|---|---|---|
| **1. 정책 읽기** | 위키의 정책을 읽고 구현 대상(확정)과 PM에게 물을 질문을 나눈다(policy). **사용자가 읽은 결과를 컨펌한다** | AI가 쓰고, 사용자가 컨펌하고, PM이 답한다 |
| **2. 문서** | domain, spec, ADR을 쓰고 점검한다. **사용자가 승인한다** | AI가 쓰고, 기계가 검사하고, 사용자가 승인 |
| **3. 계획** | plan을 쓴다. 작업마다 다루는 AC와 R의 ID를 적는다. **사용자가 승인한다** | AI가 쓰고 사용자가 승인 |
| 4. 테스트 | 구현을 보지 않고 ID마다 테스트를 쓴다 | `test-author` |
| 5. 구현 | 테스트를 통과시키는 코드를 쓴다 | 메인 세션 |
| 6. 검증 | 기계가 확인하고, 독립 리뷰어가 문서와 코드를 대조한다 | `check.sh`, `doc-reviewer`, `code-reviewer` |
| 7. 이해 (선택) | 사용자가 원할 때만 변경을 해설하고 퀴즈로 사용자의 이해를 확인한다 | `explain-diff` |
| **8. 종료** | 일지, 수정의 줄, 커밋, push, PR을 AI가 한다. **작성자 외 서버 팀원 한 명이 승인한 뒤 사람이 병합한다** | AI, 사람 |

- (1) 슬라이스는 위 여덟 단계를 순서대로 **반드시** 지나야 한다. 7단계(이해)는 사용자가 요청할 때만 한다. 검증이 실패하면 구현으로 돌아간다. [`work`의 상태 그래프와 훅]
- (2) AI는 검증을 건너뛰고 종료로 **절대** 가서는 안 된다. [`work`의 상태 그래프와 훅]
- (3) 사람이 손을 쓰는 곳은 정책 기록의 컨펌, 문서의 승인, plan의 승인, PR의 병합(작성자 외 서버 팀원 한 명의 승인과 CI 통과. CI가 생기기 전에는 CI 대신 PR에 `check.sh` 통과를 적는다)으로 **반드시** 한정해야 한다. plan이 승인되면 슬라이스 안의 일은 AI가 알아서 진행한다. [리뷰]
- (4) AI는 구현이 옳다고 판단해도 승인된 spec을 스스로 **절대** 고쳐서는 안 된다. [편집 가드 훅(한계는 "결과")과 리뷰]
- (5) AI는 문서가 비워 둔 곳을 구현이 정하면 그 결론을 문서에 적고 "확인이 필요하다"를 **반드시** 붙여야 한다. 이미 있는 요구를 바꾸는 것은 사용자만 한다. [리뷰]

### 구성 요소

| 구성 요소 | 하는 일 | 막는 실수 |
|---|---|---|
| `AGENTS.md` | 새 세션이 가장 먼저 읽는 짧은 지침(`CLAUDE.md`는 `@AGENTS.md` 한 줄로 이 파일을 불러온다). 규칙을 되풀이하지 않고 `docs/README.md`를 가리킨다 | 새 세션이 규칙을 모르는 것 |
| 스킬 `work` | 오케스트레이터. 지금 단계를 정하고 그 단계의 절차(`references/<단계>.md`)를 읽게 한다 | 단계를 건너뛰는 것, 엉뚱한 절차를 부르는 것 |
| 스킬 `review` | 문서(docs), 정책과 코드의 대조(conformance), 코드(code)의 절차와 리뷰 기록의 절차 | 쓴 사람이 자기 것을 점검하는 것, 리뷰 결과가 남지 않는 것 |
| 스킬 `status` | 지금 어느 단계인지, 남은 일이 무엇인지 보여 준다 | 상태를 AI가 추론하다 틀리는 것 |
| 스킬 `explain-diff` (선택) | 사용자가 원할 때 변경을 해설하고 퀴즈로 이해를 확인한다 | 사용자가 AI가 쓴 코드를 모르는 것 |
| 스킬 `reflect` (선택) | 일지의 "관찰"에서 같은 교정이 두 번 나왔는지 찾아 규칙이나 검사로 올리자고 제안한다 | 같은 실수의 반복 |
| 에이전트 `test-author` | AC와 R만 보고 테스트를 쓴다. 구현을 읽지 않는다 | 구현자가 자기 버그를 통과시키는 테스트를 쓰는 것 |
| 에이전트 `doc-reviewer` | 정책이 정확한가, 빠진 것이 없는가, 문서를 잘 썼는가를 점검하고, 슬라이스를 닫을 때 정책이 코드로 구현됐는지 대조한다. 읽기만 한다 | 쓴 쪽이 못 보는 모순과 빈틈, 정책대로 구현되지 않은 것 |
| 에이전트 `code-reviewer` | 코드의 성능, 코드 품질(TDA, 의존성, 네이밍, 가독성), 보안(OWASP Top 10)을 근거와 시나리오로 점검한다. 읽기만 한다 | 쓴 쪽이 못 보는 코드의 약점 |
| 훅 | 세션 시작(README와 `status` 출력을 먼저 보여 줌), `docs-lint`(문서 규칙 검사), 편집과 push 가드(`docs/spec` 편집, main push, force push, 비밀 파일 커밋을 막음), 일지 검사(코드 변경과 일지가 함께 바뀌었는지) | 규칙을 잊고 시작하는 것, 규칙 위반이 승인까지 가는 것, 위험한 push, 기록 없는 변경 |
| 스크립트 | `check.sh`(빌드, 테스트, ID 추적과 plan의 ID 검사, 키워드와 문서의 지도 검사, 지시문의 참조 검사, ArchUnit), `status.py`(문서와 git에서 단계를 계산), `policy_check.py`(위키의 정책이 정책 기록을 쓴 뒤 바뀌었는지 비교), `next.py`(시작할 수 있는 이슈, 역할 라벨로 거른다), `policy_check.py --coverage`(이슈가 없는 확정 정책) | spec과 테스트가 어긋나는 것 |

- (6) 단계의 순서는 `work` 스킬이 **반드시** 정해야 한다. 단계마다의 절차는 `work/references/<단계>.md`에 **반드시** 둬야 한다. [`ref_check.py`(라우트 파일이 있는지)와 리뷰]
- (7) 각 단계는 읽는 문서를 plan 작업의 ID로 **반드시** 좁혀야 한다. 작업이 `AC-1.2`와 `R-1.1`이면 그 줄만 읽는다. [리뷰]
- (8) `test-author`는 `src/main`을 **절대** 읽어서는 안 된다. [에이전트의 도구 제한 (강제할 수 있는지는 실험한다)]
- (9) `doc-reviewer`와 `code-reviewer`는 파일을 **절대** 고쳐서는 안 된다. 위반 목록만 돌려준다. [에이전트의 도구 제한]
- (10) 상태는 **절대** 파일로 저장해서는 안 된다. `status`는 문서와 git에서 계산한다. [`docs-lint`의 L5(`docs/`에 상태 파일의 자리가 없다)와 리뷰]

### 문서가 낡지 않게

낡을 수 있는 문서는 spec, domain, ADR, `AGENTS.md`, 스킬뿐이다. 일지, 리뷰, 닫은 plan은 쌓기만 해서 낡지 않는다.

- (11) spec의 모든 AC와 domain의 모든 R에는 ID가 **반드시** 있어야 하고, 그 ID를 `@Covers`로 단 테스트가 **반드시** 있어야 한다(ADR-0004의 N2.2). [`check.sh`의 ID 추적 검사]
- (12) 코드에서 만들 수 있는 문서(API 문서)는 손으로 **절대** 써서는 안 된다. [`docs-lint`의 L5(`docs/`에 API 문서의 자리가 없다)와 리뷰]
- (13) 슬라이스를 닫을 때 문서의 MUST를 네 가지로 나눠 **반드시** 대조해야 한다: 지키고 테스트가 강제한다, 지키지만 강제가 없다, 어긋난다, 아직 없다. 어긋남이 남아 있으면 닫지 못한다. [`review`의 대조 절차와 `doc-reviewer`]
- (14) 같은 교정이 두 번 나오면 AI는 그것을 규칙이나 검사로 올리자고 제안**할 수 있다**. [`reflect`]

### 규칙을 두는 곳

- (15) 코드의 규칙은 검사(ArchUnit, 포매터, 훅), 기준 코드, ADR의 순서로 **반드시** 둬야 한다. 앞의 것으로 지킬 수 있으면 뒤의 것에 쓰지 않는다. ADR에는 AI가 기본으로는 틀릴 판단만 쓴다. [리뷰]

### 코드 리뷰

- (16) 코드 리뷰는 Claude 모델의 `doc-reviewer`와 `code-reviewer`로 **반드시** 해야 한다. [리뷰]
- (17) AI는 코드를 다른 모델의 서비스에 **절대** 보내서는 안 된다. [권한 설정(`gemini` 명령은 매번 확인)]
- (18) `doc-reviewer`와 `code-reviewer`는 서로의 리포트를 **절대** 읽어서는 안 된다. 합치는 것은 호출한 쪽이다. [리뷰]

### 에이전트의 통신

에이전트는 서브에이전트 방식으로 부른다. 메인 세션이 에이전트를 하나씩 부르고, 에이전트는 결과를 돌려주고 끝난다. 팀 방식(에이전트가 독립된 세션으로 떠서 서로 메시지를 보냄)은 쓰지 않는다. 이유: 이 프로젝트는 단계를 순서대로 가고 사람 확인 지점이 단계마다 정해져 있어서 병렬 협업이 필요 없다. 비용이 낮고, 두 리뷰어가 서로 보고서를 읽지 않는 규칙(18번)이 구조로 지켜진다.

- (19) 에이전트는 다른 에이전트에게 메시지를 **절대** 보내서는 안 된다. 에이전트를 부르는 것은 메인 세션뿐이다. [에이전트의 도구 제한 (`Agent`와 `SendMessage`를 주지 않는다)]
- (20) 리뷰어는 리포트를 최종 응답으로 **반드시** 돌려주어야 한다. 리포트를 `docs/review/`에 저장하는 것은 호출한 메인 세션이다. [에이전트의 도구 제한 (리뷰어에게 Write가 없다)]

팀 방식이 필요해지면(여러 슬라이스를 병렬로 돌릴 때) 이 절을 고쳐서 다시 정한다.

### 중간 산출물

리뷰어의 리포트는 받는 즉시 슬라이스의 리뷰 문서(`docs/review/`)에 기록한다. 끊겼을 때 다시 시작하는 장치(`_workspace/<run-id>/`, 아래 21~23번)는 뺐다(2026-11-24 일지 스텝 14). `_workspace/`에는 에이전트에게 넘기는 diff와 `test-author`의 노트만 둔다. 이 폴더는 git에 올리지 않는다.

- (21) (폐기, 2026-11-24 일지 스텝 14) 메인 세션은 에이전트의 최종 응답을 받으면 고치지 않고 `_workspace/<run-id>/`에 파일로 **반드시** 저장해야 한다. [리뷰]
- (22) (폐기, 2026-11-24 일지 스텝 14) 메인 세션은 에이전트를 부르기 전에 같은 `<run-id>`의 산출물이 있는지 **반드시** 확인해야 한다. 산출물이 현재 커밋과 맞으면 에이전트를 다시 부르지 않는다. [리뷰]
- (23) (폐기, 2026-11-24 일지 스텝 14) `status.py`는 `docs/review/`에 아직 옮기지 않은 리포트와 현재 커밋보다 낡은 diff를 **반드시** 알려야 한다. [`status.py`]


### 문서가 코드와 어긋날 때

README의 "기준"이 방향을 정한다. 코드와 spec이 다르면 코드를 고친다. 사용자가 코드가 옳다고 판단하면 spec을 먼저 고친다. 아래 요구는 그 길을 훅이 막지 않게 하는 절차와, 슬라이스 밖의 수정이 spec을 건너뛰지 않게 하는 절차를 정한다.

- (24) AI는 사용자가 코드가 옳다고 판단하면 plan의 상태를 승인에서 제안으로 **반드시** 되돌려야 한다. [리뷰]
- (25) AI는 spec을 고친 뒤 plan의 승인을 사용자에게 **반드시** 다시 받아야 한다. [편집 가드 훅 (승인 전에는 `src/main`을 고치지 못한다)]
- (26) AI는 사용자가 말하지 않았는데 plan의 상태를 승인에서 제안으로 **절대** 바꿔서는 안 된다. [리뷰]
- (27) AI는 슬라이스 밖에서 `src/main`의 동작을 바꾸면(테스트의 기대값이 달라지면) 영향받는 AC와 R의 테스트가 통과하는지 **반드시** 확인해야 한다. [`check.sh`]
- (28) AI는 슬라이스 밖의 수정이 spec의 요구와 다르면 고치기 전에 사용자에게 **반드시** 올려야 한다. [리뷰]

26번은 훅이 확인하지 못한다. 훅은 plan의 상태 줄만 보고 사용자의 말을 모르기 때문이다. 그래서 리뷰와 일지의 기록(`결정 (사용자)`)이 확인한다.

### 하네스 부품을 만들 때

- (29) AI는 에이전트, 스킬, 훅을 만들거나 역할을 바꾸기 전에 "누가, 무엇을, 무엇을 못 하는가"를 표로 사용자에게 **반드시** 보이고 승인을 받아야 한다. [리뷰]
- (30) AI는 사용자가 그 표를 승인하기 전에 부품의 파일을 **절대** 써서는 안 된다. [리뷰]

표의 열은 부품의 이름, 누가(무엇인가), 무엇을(맡는 일), 무엇을 못 하는가다. 에이전트는 읽는 문서와 도구도, 훅은 언제 도는지도 더한다. 이유: 부품의 역할을 AI가 정하고 만들면 사용자가 원한 것과 어긋나서 다시 만들게 된다(AI가 역할을 정하고 만들면 어긋난 것을 다시 만들게 된다).

### 리뷰의 기록

- (31) AI는 리뷰어의 리포트를 `docs/review/`에 **반드시** 기록해야 한다. 지적을 요약하거나 고치지 않고 그대로 옮긴다. [리뷰]
- (32) AI는 지적마다 처리(받아들임, 받아들이지 않음, 보류)와 이유와 결정한 사람을 **반드시** 적어야 한다. 처리가 없는 리뷰가 있으면 슬라이스를 닫지 못한다. [`status.py`의 처리 대기 표시, `docs-lint`의 L6(처리의 값, `받아들이지 않음`은 사용자), 종료 절차]
- (33) 메인 세션은 한 대상의 리뷰를 2라운드에서 **반드시** 끝내야 한다. 2라운드 뒤에 남은 차단은 사용자가 승인 관문에서 정한다. [리뷰]

`받아들이지 않음`은 사용자만 정한다. AI는 리뷰어의 지적을 스스로 거절하지 않는다. 처리는 리뷰 문서에 "처리"의 절로 더하고 이미 쓴 줄은 고치지 않는다(README의 "쌓기만 한다").

## 결과

- 사용자가 손을 쓰는 곳(요구 3)마다 슬라이스 하나에 한 번씩 확인한다. 퀴즈는 선택이다. 나머지는 AI가 하고 기계가 막는다.
- 하네스를 첫 슬라이스 전에 만들어야 해서 코드보다 하네스가 먼저 나온다.
- 글로 쓴 설명이 의미상 낡았는지는 기계가 완전히 알 수 없다. 그래서 요구를 ID와 테스트가 있는 형태로 쓰고, 남은 글은 슬라이스를 닫을 때 `doc-reviewer`가 본다(요구 11과 13).
- 요구 8은 훅(`restrict-test-author.sh`)이 강제한다. 실제 `test-author` 호출에서 `src/main`의 Read와 Write, 허용하지 않은 Bash(`git status`)가 막히고, `docs`의 Read와 `src/test`의 Write는 통과하는 것을 확인했다(2026-11-24 일지 스텝 5). 훅은 `src/main`의 Read와 경로를 지정한 Grep, Glob을 막고, 경로 없이 저장소 전체를 찾는 것은 막지 못한다.
- 편집 가드 훅(`guard-edit.sh`)은 Edit, Write, MultiEdit만 본다. Bash의 `sed -i`나 `cat >`로 쓰는 것은 막지 못한다. spec 잠금은 plan 파일의 상태 줄로 판정하는데, 그 줄을 AI가 고치는 것도 막지 못한다. `src/main`은 승인된 plan이 없어도 막지 않고 알린다. 그래서 spec 잠금의 우회는 PR의 리뷰가 확인한다. 우회가 실제로 일어나면 일지의 "관찰"에 적고 `check.sh`에 검사를 더한다.
- push 가드(`pre-push-check.sh`)는 명령의 글자를 읽어서 판정한다. 별칭이나 변수로 감싼 push는 보지 못하고, heredoc의 본문에 그 글자가 있으면 push가 아닌 명령도 검사한다. 사람이 터미널에서 하는 push는 CI와 브랜치 보호가 막는다.
- 훅은 `jq`로 입력을 읽고, 읽지 못하면 통과시킨다. `jq`가 없는 컴퓨터에서는 훅이 말없이 꺼진다. 그래서 `session-start.sh`가 `jq`가 없으면 경고하고, `AGENTS.md`의 "시작할 때"에 설치를 적었다.
