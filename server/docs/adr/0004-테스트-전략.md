# ADR-0004. 테스트 전략

- 상태: 제안 (AI가 제안. 팀의 승인 전이다)

읽는 법은 `.claude/skills/work/references/doc-style.md`를 따른다. 굵은 키워드가 없는 문장은 설명이다.

## 맥락

이 ADR의 테스트 규칙(N1~N4, V1~V6, E1~E5, F1~F4)은 AI가 제안했고, 사용자가 2026-11-23에 묶음마다 확인했다.

예시는 따닥의 위키 정책(UPL-01~04, UPL-17)으로 썼다. 코드가 생기면 예시의 이름은 domain의 용어 표를 따른다.

| 용어 | 뜻 |
|---|---|
| 요구사항 | 이 시스템이 지켜야 한다고 정한 동작. 이 프로젝트에서는 spec의 AC와 domain의 R이다 |
| 단위 테스트 | 한 구성요소 안의 객체들이 함께 동작하는 것을 DB와 네트워크 없이 확인하는 테스트 |
| 통합 테스트 | 서로 다른 구성요소(응용 계층, 저장소, DB 등)를 실제로 연결해서 확인하는 테스트 |
| 응용 계층 통합 테스트 | 응용 계층, 저장소, DB를 연결하는 통합 테스트. 응용 계층은 실제다 |
| 표현 계층 테스트 | 표현 계층(컨트롤러), 필터, 직렬화 같은 웹 계층을 확인하는 통합 테스트. 응용 계층은 대역이다. HTTP 약속(요청과 응답의 약속)만 확인한다 |
| E2E 테스트 | 여러 요청을 이은 시나리오 하나를 요청부터 DB까지 확인하는 테스트 |
| fake | 직접 만든 가짜. 받은 내용을 기록한다 |
| 목 | 호출 여부를 검증하는 대역 |
| Fixture | 기본값이 채워진 객체 생성 도우미 |
| 불변식 | 언제나 참이어야 하는 조건 |
| 외부 시스템 | 우리 서버 밖의 시스템 (소셜 로그인 제공사, AI 모델 API 등). ADR-0003의 용어와 같다 |

## 결정

요구마다 끝의 대괄호에 지키는 것을 적는다. `[리뷰]`는 검사로 만들지 못한 요구이고 코드 리뷰가 확인한다. `[리뷰 (검사로 바꿀 수 있다)]`는 같은 교정이 두 번 나오면 검사로 만든다. 검사가 생기면 그 줄은 이 ADR에서 뺀다.

### 작성 (N)

#### N1. 한 테스트는 한 시나리오

- (N1.1) 테스트는 한 시나리오(한 규칙)의 결과만 **반드시** 확인해야 한다. [리뷰]

좋은 예: "텍스트 PDF를 올리면 자료가 저장된다"는 이름, 형식, 올린 시각 세 가지를 확인한다. 한 결과를 설명하는 세 가지다. 나쁜 예: "텍스트 PDF를 올리면 저장되고 텍스트가 추출된다"는 서로 다른 두 규칙이 섞였다.

서로 다른 규칙이 한 테스트에 있으면 실패했을 때 어느 요구사항이 문제인지 흐려진다. 이름으로 테스트 내용을 요약할 수 없으면 테스트를 나누라는 신호다. 확인하는 assert의 개수가 아니라 결과를 설명하는 만큼 쓴다.

#### N2. 이름은 조건 + 행동 → 결과 한 문장

- (N2.1) 테스트의 이름은 도메인 용어로 쓴 "조건 + 행동 → 결과" 한 문장으로 **반드시** 써야 한다. [리뷰 (검사로 바꿀 수 있다)]
- (N2.2) 테스트는 확인하는 요구사항의 ID(spec의 AC, domain의 R)를 `@Covers("AC-2.5")` 애너테이션으로 **반드시** 달아야 한다. [`trace_check.py`]
- (N2.3) 테스트의 이름에 기술 용어(상태 코드, 테이블, 예외 클래스 이름)와 정보가 없는 말(`test1`, `정상_동작`)을 **절대** 써서는 안 된다. [리뷰 (검사로 바꿀 수 있다)]

기술 용어는 확인하는 코드 안에서 다룬다. 요구사항의 ID는 이름이 아니라 애너테이션으로 단다. 이름은 한 문장의 도메인 용어로 두기 위해서다. 요구사항 하나에 테스트가 여럿일 수 있고(경계값 세 점, "안 돼요"마다 하나), 한 테스트가 ID 여럿을 다룰 수 있어서 `@Covers`는 ID 여러 개를 받는다(`@Covers({"AC-1.1", "R-1.2"})`). 이름의 접두어와 `@DisplayName`은 쓰지 않는다. 이 선택은 사용자가 2026-11-23에 정했다.

| 나쁜 이름 | 이유 | 좋은 이름 |
|---|---|---|
| `업로드하기_413` | 기술 용어이고 조건이 없다 | 20MB를 넘는 파일을 올리면 거절된다 |
| `업로드하기_성공` | 무엇이 일어나는지 없다 | 텍스트 PDF를 올리면 자료가 저장되고 올린 시각이 남는다 |
| `uploadTest2` | 정보가 없다 | (위와 같이 쓴다) |

#### N3. 구조는 준비, 실행, 검증

- (N3.1) 테스트는 준비, 실행, 검증 세 덩어리를 빈 줄로 **반드시** 나눠야 한다. [리뷰]

실행은 보통 한 줄이다. 실행이 여러 줄이면 시나리오가 둘이라는 신호다.

#### N4. 같은 모양에 값만 다르면 합친다

- (N4.1) 입력 모양이 같고 값만 다른 케이스는 매개변수화 테스트 하나로 **반드시** 합쳐야 한다. [리뷰]

경계값 세 점(V2)이 매개변수화 테스트의 대표적인 경우다. 쪼개는 기준은 항목 수가 아니라 시나리오다 (N1).

### 검증 범위 (V)

#### V1. "안 돼요"마다 거절되는지 확인한다

- (V1.1) 요구사항이 "안 돼요"라고 정한 조건마다, 거절되는지 확인하는 테스트를 최소 하나 **반드시** 써야 한다. [리뷰 (검사로 바꿀 수 있다)]

| 요구사항의 "안 돼요" | 테스트 |
|---|---|
| 스캔·사진 PDF는 받지 않는다 (UPL-02) | 스캔 PDF를 올리면 거절된다 |
| 한 번에 20MB까지다 (UPL-03) | 20MB를 넘는 파일을 올리면 거절된다 |
| hwp 파일은 받지 않는다 (UPL-17) | hwp 파일을 올리면 거절된다 |
| URL은 받지 않는다 (UPL-02) | URL을 올리면 거절된다 |

사고는 거절해야 할 때 거절하지 않는 곳에서 난다. 이 서비스에서는 받지 않기로 한 형식이 통과해 텍스트 추출까지 가는 것이 그 예다. "안 돼요" 목록이 그대로 테스트 목록이 되므로, 하나라도 빠지면 누락이 보인다.

#### V2. 임계값은 직전, 정확히, 직후 세 점

- (V2.1) 임계값이 있는 규칙은 직전, 정확히, 직후 세 점을 모두 **반드시** 확인해야 한다. [리뷰]
- (V2.2) AI와 사용자는 요구사항이 정하지 않은 경계를 추측으로 **절대** 써서는 안 된다. [리뷰]
- (V2.3) AI와 사용자는 요구사항이 정하지 않은 경계를 질문으로 **반드시** 올려야 한다. [리뷰]

예: 위키 UPL-03은 "20MB까지"라고 정했다.

| 파일 크기 | 결과 |
|---|---|
| 20MB보다 1바이트 작다 | 받는다 (직전) |
| 정확히 20MB | 정해지지 않았다 (정확히) |
| 20MB보다 1바이트 크다 | 거절한다 (직후) |

"정확히 20MB"에서 요구사항이 답을 주지 않는다("까지"가 20MB를 포함하는지, MB가 1000×1000인지 1024×1024인지). 경계값 테스트는 이렇게 요구사항의 빈틈을 드러내는 도구이기도 하다. 이 경계는 spec에서 정해야 한다.

#### V3. 입력 검증은 요구사항에 적힌 것만

- (V3.1) 테스트는 요구사항에 숫자나 조건이 적힌 입력 제한만 **반드시** 확인해야 한다(경계값은 V2.1). [리뷰]
- (V3.2) 테스트는 프레임워크가 보장하는 동작과 요구사항에 없는 일반 검증(null, 빈 값의 일반 처리)을 **절대** 확인해서는 안 된다. [리뷰]

입력 제한이 어노테이션 같은 설정으로 구현되어 있으면, 설정을 빠뜨리거나 숫자를 잘못 적어도 컴파일과 실행은 멀쩡하다. 테스트가 없으면 요구사항이 조용히 사라진다. 우리가 확인하는 것은 프레임워크가 아니라 "우리 요구사항이 실제로 걸려 있는가"다.

#### V4. 같은 규칙은 가장 낮은 계층 한 곳이 전수로 확인한다

- (V4.1) 단위 테스트는 규칙의 진리표 전부를 **반드시** 확인해야 한다. [리뷰]
- (V4.2) 통합 테스트, 표현 계층 테스트, E2E 테스트는 규칙의 조합을 **절대** 반복해서는 안 된다. [리뷰]

같은 조합을 여러 계층에서 반복하면 테스트가 늘고, 규칙을 고칠 때 고칠 곳도 늘어난다. 각 테스트가 무엇을 확인하는지는 용어 표가 정한다.

#### V5. E2E는 대표 흐름만

- (V5.1) E2E 테스트는 요구사항의 핵심 시나리오 몇 개만 **반드시** 써야 한다. 몇 개인지는 정하지 않았다. [리뷰]

규칙은 단위 테스트와 통합 테스트가 이미 확인했으므로(V4.2), E2E 테스트는 조립이 맞는지만 본다. 규칙을 다시 따지면 가장 느린 테스트가 다른 테스트의 일을 비싸게 반복한다.

#### V6. 우리 코드의 공개된 행위만 확인한다

- (V6.1) 테스트는 우리 코드가 바깥에 드러내는 공개된 행위의 결과로 **반드시** 확인해야 한다. [리뷰]
- (V6.2) 테스트는 비공개 메서드를 직접 **절대** 확인해서는 안 된다. 리플렉션으로 여는 것도 같다. [리뷰 (검사로 바꿀 수 있다)]

비공개 메서드는 그것을 쓰는 공개된 행위를 통해 이미 확인된다. 직접 확인하면 구현 세부에 묶여서 리팩터링만 해도 깨진다. 비공개 메서드의 로직이 따로 확인해야 할 만큼 복잡하면, 독립된 클래스로 분리해서 공개하라는 신호다.

### 테스트 환경 (E)

#### E1. 외부 시스템은 fake가 기본

- (E1.1) 테스트는 외부 시스템(소셜 로그인 서버, AI 모델 API)을 fake로 **반드시** 대체해야 한다. [리뷰]
- (E1.2) AI와 사용자는 호출 자체가 요구사항인 경우가 아니면 목을 **절대** 써서는 안 된다. 예: 재시도는 최대 3번이다. [리뷰]
- (E1.3) 내부 협력 객체(저장소 등)는 대역 없이 실제 DB로 **반드시** 확인해야 한다. [리뷰]

fake는 보낸 내용을 기록하므로 결과로 확인할 수 있다. 예: AI 모델 fake가 받은 요청을 목록에 쌓고, 테스트는 "AI 모델 fake에 추출한 텍스트가 한 번 전달됐다"를 확인한다.

실제 외부 시스템을 부르면 네트워크 상태와 상대 시스템의 상태에 따라 결과가 달라지고, 느리고, 요금이 나가는 것 같은 부작용이 생긴다.

#### E2. 시간과 무작위는 주입한다

- (E2.1) 코드는 현재 시각과 난수를 직접 읽지 않고 **반드시** 주입받아야 한다. 테스트는 주입한 값에 고정값을 쓴다. [리뷰 (검사로 바꿀 수 있다)]
- (E2.2) 테스트는 `sleep`으로 시간을 **절대** 기다려서는 안 된다. [리뷰 (검사로 바꿀 수 있다)]

"1시간 경과"를 확인하려고 1시간을 기다릴 수 없고, 짧게 기다리는 흉내는 느리고 가끔 실패하는 테스트가 된다. 시각을 직접 지정하면 경계값 세 점(V2)도 정확히 만들 수 있다. 임시 파일 이름 생성처럼 무작위가 있으면 생성기를 주입한다. 시각의 형식과 시간대는 정하지 않았고 코드가 기준이다(ADR-0006의 "정하지 않은 것" 1번).

#### E3. 동시성은 불변식으로 확인한다

- (E3.1) 동시성 테스트는 결과를 불변식으로 **반드시** 확인해야 한다. 예: 성공은 정확히 1건이다. [리뷰]
- (E3.2) 동시성 테스트는 누가 성공했는지를 **절대** 확인해서는 안 된다. [리뷰]
- (E3.3) 동시성 테스트가 한 번이라도 실패하면 구현 버그의 신호로 **반드시** 봐야 한다. [리뷰]
- (E3.4) AI와 사용자는 동시성 테스트가 flaky라고 **절대** 넘겨서는 안 된다. [리뷰]

예(가정이고 실제 규칙은 spec에서 정한다): 세 요청이 같은 회차 구분 결과를 동시에 저장하려 한다. 확인: 저장된 결과는 정확히 1건이다.

모든 스레드를 신호 한 번에 출발시키는 방법과 스레드 수는 동시성 테스트 도우미 코드가 기준이다. 누가 이기는지는 정해져 있지 않다. flaky라고 넘기면 가장 중요한 버그를 놓친다. 트랜잭션 롤백에 기대지 않는 것은 E5.3이다.

#### E4. 테스트 데이터는 Fixture로 만들고, 결과를 좌우하는 값은 드러낸다

- (E4.1) 테스트는 객체를 Fixture로 **반드시** 만들어야 한다. [리뷰]
- (E4.2) 테스트는 결과를 좌우하는 값을 테스트 안에서 **반드시** 직접 적고, 시나리오와 무관한 값은 Fixture의 기본값에 맡겨야 한다. [리뷰]
- (E4.3) 테스트는 자기 데이터를 **반드시** 직접 만들어야 한다. 다른 테스트가 만든 데이터에 기대면 순서에 따라 결과가 달라진다. [리뷰]

예: 파일 크기와 형식은 결과를 좌우하므로 직접 적고, 자료의 제목과 올린 사용자의 이름은 이 시나리오와 무관하므로 Fixture의 기본값에 맡긴다. 기본값에 몰래 기대면 읽는 사람이 근거를 알 수 없고, 기본값을 바꾸는 순간 상관없는 테스트가 줄줄이 깨진다. Fixture의 이름, 오버로드, 저장의 방식은 기준 Fixture 코드가 보여 준다.

#### E5. DB는 매 테스트 전에 비운다

- (E5.1) 테스트는 시작하기 전에 DB의 데이터를 **반드시** 비워야 한다. [리뷰]
- (E5.2) DB를 쓰는 테스트는 로컬과 CI에서 운영과 같은 종류의 DB를 Testcontainers로 **반드시** 써야 한다(ADR-0002의 요구 15). [테스트 기반 클래스 (리뷰)]
- (E5.3) 테스트는 롤백에 **절대** 기대서는 안 된다. [리뷰]

롤백은 편하지만 실제 커밋 시점의 동작(제약 위반 등)을 놓치고, 동시성 테스트에서는 쓸 수 없다. 테스트가 끝난 뒤가 아니라 시작 전에 비우면, 앞선 테스트가 중간에 실패해도 영향을 받지 않는다. 비우는 일은 테스트 기반 클래스가 한다. 동시성 테스트(E3)는 운영 DB의 잠금에서만 믿을 수 있어서 같은 종류의 DB에서 돌린다.

### 실패와 변경 (F)

#### F1. 실패하면 누가 틀렸는지 먼저 가린다

- (F1.1) AI와 사용자는 실패의 원인이 구현, 요구사항, 테스트 중 어느 쪽인지 정하기 전에 코드를 **절대** 고쳐서는 안 된다. [리뷰]
- (F1.2) AI와 사용자는 기대값을 구현의 현재 동작에 맞추거나 통과시키려고 확인하는 내용을 약하게 **절대** 바꿔서는 안 된다. [리뷰]

기대값을 구현에 맞추면 테스트는 요구사항을 검증하는 대신 구현을 받아 적는 기록이 된다. 기대값이 바뀌는 유일한 경우는 요구사항이 바뀐 때이고, 이때는 spec 변경이 먼저다. 요구사항이 틀렸거나 모호할 때 결정은 사용자가 한다. `docs/README.md`의 "기준"과 같다.

#### F2. 테스트를 끄지 않는다

- (F2.1) AI와 사용자는 `@Disabled`와 skip 같은 비활성화를 **절대** 써서는 안 된다. [리뷰 (검사로 바꿀 수 있다)]

꺼 둔 테스트는 대부분 다시 켜지지 않는다. 켜지지 않는 순간 그 요구사항은 확인되지 않은 채 남는다. 지금 통과시킬 수 없다면 이유를 F1에서 찾는다.

#### F3. 버그는 재현 테스트부터

- (F3.1) AI와 사용자는 버그를 발견하면 코드를 고치기 전에 그 버그를 재현하는 실패 테스트를 **반드시** 먼저 써야 한다. [리뷰]

같은 버그가 돌아오면 이 테스트가 막는다. 이것이 회귀 테스트다. 회귀는 테스트의 종류가 아니라 모든 테스트가 겸하는 목적이다.

#### F4. red를 확인하고, 실패하는 테스트를 공유 브랜치에 남기지 않는다

- (F4.1) AI와 사용자는 테스트를 쓴 뒤 구현하기 전에 실행해서 red를 **반드시** 확인해야 한다. 컴파일 실패도 red다. 버그를 재현하는 테스트(F3.1)도 같다. 실패하지 않으면 재현이 아니다. [리뷰]
- (F4.2) AI와 사용자는 실패하는 테스트를 공유 브랜치에 **절대** 남겨서는 안 된다. [CI]

TDD에서는 구현 전에 테스트가 일부러 실패한다. 이 상태를 오래 두지 않는 구조가 답이다. 숨기려고 F2를 어기지도 않는다. 테스트와 구현을 함께 커밋하는 규칙은 ADR-0005에서 정한다.
