# ADR-0007. 오류 응답

- 상태: 승인 (사용자가 결정, 2026-11-23 일지 스텝 4)
- 수정 (2026-11-23 일지 스텝 8): 공통 예외의 이름을 `TtadakException`에서 `CustomException`으로 바꿨다. 사용자가 요청했다. 확인이 필요하다.
- 수정 (2026-11-24 일지 스텝 9): 공통 오류 코드에 `DEFAULT_NOT_FOUND`(404)와 `DEFAULT_CONFLICT`(409)를 더하고 요구 22와 "정하지 않은 것" 7번을 더했다. 사용자가 400, 401, 403, 404, 409를 두자고 했다. 확인이 필요하다.
- 수정 (2026-11-24 일지 스텝 10): 응답의 모양을 ProblemDetail에서 메멘토의 `ApiResponse`로 바꿨다. 요구 1, 2, 3, 4, 9, 17을 고치고 요구 23을 더했고 "정하지 않은 것" 4번과 7번을 정리했다. 사용자가 간편하고 깔끔해서 바꾸자고 했다. 확인이 필요하다.
- 수정 (2026-11-24 일지 스텝 11, 12): 스텝 11에서 전역 예외 처리기를 예외마다 핸들러를 두는 모양으로 바꿨다가, 스텝 12에서 사용자가 너무 세세하다고 해서 부모 클래스를 상속하고 `CustomException`과 `Exception`만 직접 잡는 모양으로 되돌렸다. 요구 17, 18, 23과 "정하지 않은 것" 7번과 "결과"를 이에 맞췄다. 확인이 필요하다.

읽는 법은 `.claude/skills/work/references/doc-style.md`를 따른다. 굵은 키워드가 없는 문장은 설명이다.

## 맥락

모든 API는 같은 모양의 오류 응답을 내려야 클라이언트가 한 가지 방법으로 오류를 읽는다. 사용자가 2026-11-23에 오류 코드를 메멘토처럼 enum 하나에 모으자고 정했고, 2026-11-24에 응답의 모양도 메멘토의 `ApiResponse`로 하자고 정했다(처음에는 AuDDum의 ProblemDetail로 정했다가 바꿨다). 아래 요구는 그 결정을 옮긴 AI의 제안이다. ADR-0003의 "정하지 않은 것" 3번(예외의 분류와 오류 응답의 형식)을 이 ADR이 정한다. 기능이 쓰는 오류 코드(예: 자료 없음)는 각 기능의 spec이 정한다. 이 ADR은 공통 코드와 형식과 코드를 두는 방식만 정한다.

| 용어 | 뜻 |
|---|---|
| 오류 코드 | 오류의 종류를 가리키는 이름. 영문 대문자와 밑줄로 쓴다(예: `DEFAULT_VALIDATION_FAILED`). 코드마다 HTTP 상태, 메시지, 로그 수준이 하나씩 붙는다 |
| 공통 오류 코드 | 기능과 상관없이 모든 API가 쓰는 오류 코드. 이름이 `DEFAULT_`로 시작한다 |
| 기능의 오류 코드 | 한 기능이 정하는 오류 코드. 이름이 기능의 접두어로 시작한다(예: `MEMBER_NOT_FOUND`) |
| ApiResponse | 모든 API 응답의 공통 틀. `result`(`SUCCESS`나 `ERROR`), `data`(성공의 값), `error`(오류 정보)를 가진다 |
| 전역 예외 처리기 | 컨트롤러에서 나온 모든 예외를 잡아 오류 응답으로 바꾸는 한 곳 |

## 결정

요구마다 끝의 대괄호에 지키는 것을 적는다. `[리뷰]`는 검사로 만들지 못한 요구이고 코드 리뷰가 확인한다.

### 응답의 모양

- (1) 서버는 성공과 오류를 모두 `ApiResponse`로 **반드시** 내려야 한다. 본문의 형식은 `application/json`이다. [표현 계층 테스트]
- (2) 오류 응답은 `result`를 `ERROR`로, `data`를 null로, `error`를 `status`, `code`, `message`, `data`로 **반드시** 채워야 한다. `code`는 오류 코드의 이름이고 `message`는 오류 코드의 메시지다. [표현 계층 테스트]
- (3) 입력 검증이 실패한 응답은 `error.data`에 `field`와 `reason`을 가진 항목의 목록을 **반드시** 담아야 한다. 검증 실패가 아닌 오류 응답의 `error.data`는 null이다. [표현 계층 테스트]
- (4) 오류 응답의 HTTP 상태는 `error.status`와 같은 값으로 **반드시** 내려야 한다. 그래서 오류가 HTTP 200으로 내려가는 일은 없다. [표현 계층 테스트]
- (5) 서버는 스택 트레이스와 내부 예외의 메시지를 오류 응답에 **절대** 담아서는 안 된다. [표현 계층 테스트]

### 오류 코드

- (6) 서버는 모든 오류 코드를 enum `ErrorCode` 하나에 **반드시** 모아야 한다. [리뷰]
- (7) 오류 코드는 HTTP 상태, 메시지, 로그 수준을 **반드시** 하나씩 가져야 한다. [리뷰]
- (8) 오류 코드 하나는 HTTP 상태 하나에만 **반드시** 묶여야 한다. [리뷰]
- (9) 서버는 공통 오류 코드를 `ErrorCode`에 **반드시** 둬야 한다. 값은 아래 표와 같다. [표현 계층 테스트]
- (10) 기능의 오류 코드는 이름을 `<기능>_<사유>`로 **반드시** 지어야 한다. [리뷰]
- (11) 기능의 오류 코드는 `ErrorCode` 안에서 기능별로 묶어 **반드시** 적어야 한다. [리뷰]
- (12) AI와 사용자는 오류 코드의 이름을 바꾸는 것을 **절대** 해서는 안 된다. 클라이언트가 `code`로 분기하기 때문이다. [리뷰]

| 공통 오류 코드 | HTTP 상태 | 메시지 | 로그 수준 |
|---|---|---|---|
| `DEFAULT_MALFORMED_REQUEST` | 400 | 요청 형식이 올바르지 않습니다. | INFO |
| `DEFAULT_VALIDATION_FAILED` | 400 | 요청 값이 올바르지 않습니다. | INFO |
| `DEFAULT_UNAUTHENTICATED` | 401 | 로그인이 필요합니다. | WARN |
| `DEFAULT_FORBIDDEN` | 403 | 권한이 없습니다. | WARN |
| `DEFAULT_NOT_FOUND` | 404 | 요청한 리소스를 찾을 수 없습니다. | INFO |
| `DEFAULT_METHOD_NOT_ALLOWED` | 405 | 지원하지 않는 요청 방식입니다. | INFO |
| `DEFAULT_CONFLICT` | 409 | 요청이 현재 상태와 충돌합니다. | INFO |
| `DEFAULT_UNSUPPORTED_MEDIA_TYPE` | 415 | 지원하지 않는 요청 본문 형식입니다. | INFO |
| `DEFAULT_INTERNAL_ERROR` | 500 | 서버 내부 오류가 발생했습니다. | ERROR |

### 예외와 처리

- (13) 서버는 `ErrorCode`를 가진 공통 예외 `CustomException`을 **반드시** 둬야 한다. [리뷰]
- (14) 코드는 업무 오류를 `CustomException`으로 **반드시** 던져야 한다. [리뷰]
- (15) 입력 검증 실패는 필드와 사유를 담은 `CustomException`(`DEFAULT_VALIDATION_FAILED`)으로 **반드시** 던져야 한다. [리뷰]
- (16) 전역 예외 처리기는 `CustomException`을 그 오류 코드의 HTTP 상태와 `code`로 **반드시** 바꿔야 한다. [표현 계층 테스트]
- (17) 전역 예외 처리기는 Bean Validation 실패(요청 본문)을 `DEFAULT_VALIDATION_FAILED`와 `error.data`로 **반드시** 바꿔야 한다. [표현 계층 테스트]
- (18) 전역 예외 처리기는 요청 본문의 형식 오류, 파라미터의 타입 불일치, 필수 파라미터의 누락, 요청 파라미터의 검증 실패 같은 Spring MVC의 400 응답을 `DEFAULT_MALFORMED_REQUEST`로 **반드시** 바꿔야 한다. [표현 계층 테스트]
- (19) 전역 예외 처리기는 처리하지 못한 예외를 `DEFAULT_INTERNAL_ERROR`로 **반드시** 바꿔야 한다. [표현 계층 테스트]
- (20) 전역 예외 처리기는 오류를 오류 코드의 로그 수준으로 **반드시** 한 번만 남겨야 한다. [리뷰]
- (21) 예외를 던지는 쪽은 같은 오류를 로그로 **절대** 다시 남겨서는 안 된다. 코드 컨벤션의 "던지거나 남기거나 하나만"과 같다. [리뷰]
- (22) 전역 예외 처리기는 존재하지 않는 경로 같은 Spring MVC의 404 응답에 `DEFAULT_NOT_FOUND`를 **반드시** 붙여야 한다. [표현 계층 테스트]
- (23) 전역 예외 처리기는 Spring MVC의 405 응답에 `DEFAULT_METHOD_NOT_ALLOWED`를, 415 응답에 `DEFAULT_UNSUPPORTED_MEDIA_TYPE`을 **반드시** 붙여야 한다. 그 밖의 표준 4xx 응답에는 `DEFAULT_MALFORMED_REQUEST`의 코드를 붙이고 상태는 그대로 둔다. [표현 계층 테스트]

예외를 던진 곳에서 로그를 남기지 않는 이유: 던지면서 남기고 상위에서 또 남기면 같은 사건이 여러 줄이 된다.

## 정하지 않은 것

| # | 내용 | 어디서 정하나 |
|---|---|---|
| 1 | `ErrorCode`와 `CustomException`이 놓이는 패키지(공통 패키지 `support`)와 도메인 계층이 그것을 참조해도 되는지 | 첫 코드를 쓸 때. 도메인 객체가 `CustomException`을 던지면 ADR-0003의 요구 2(도메인 계층은 다른 계층을 참조하지 않는다)와 부딪히는지 확인한다. `ErrorCode`가 Spring의 `HttpStatus`를 쓰는 것도 같은 문제다 |
| 2 | 로그 수준을 오류 코드에 두는 것. 위 표의 수준은 AuDDum의 값이다 | ADR-0006의 "정하지 않은 것" 3번(로그 레벨의 구분) |
| 3 | 인증과 인가의 필터 단계에서 나오는 401과 403의 응답. 같은 형식으로 맞추는 방법은 인증 방식에 달렸다 | 계정의 spec (위키 ACC-03이 미결정) |
| 4 | 페이지 처리의 형식. 성공 응답의 틀은 `ApiResponse`로 정했다 | 첫 목록 API를 만들 때 |
| 5 | 오류 코드 목록을 문서로 보이는 방법(코드에서 생성할지, 도구가 만들 문서로 갈음할지) | 첫 API를 만들 때 (ADR-0002의 "정하지 않은 것" 1번 API 문서 도구) |
| 6 | 로그에 남기는 요청 식별자(MDC)와 요청 로그 | 정하지 않았다 |
| 7 | `DEFAULT_CONFLICT`를 던지는 기준. 406 같은 그 밖의 표준 4xx에 전용 코드를 둘지(지금은 요구 23의 대체 코드). 요청 파라미터의 검증 실패에 필드 목록을 담을지(지금은 `error.data`가 없다) | 첫 API를 만들 때 |

## 버린 대안

| 대안 | 좋은 점 | 버린 이유 |
|---|---|---|
| 오류를 ProblemDetail(RFC 7807)로 내린다(AuDDum). 처음 승인한 안이다 | Spring이 지원하는 표준이고 성공은 DTO 그대로 내려 간단하다 | 사용자가 성공과 실패의 틀이 하나인 `ApiResponse`가 더 간편하고 깔끔하다고 정해서 바꿨다(2026-11-24) |
| 오류 코드를 `ErrorCode` 인터페이스와 도메인별 enum(`MemberErrorCode`)으로 나눈다(AuDDum) | 도메인마다 파일이 나뉘어 충돌이 적다 | 사용자가 enum 하나로 정했다(2026-11-23). 코드가 한 곳에 모여 이름이 겹치는지 한눈에 보인다 |

## 결과

- 성공과 실패가 같은 틀이라 클라이언트가 `result`로 먼저 가를 수 있다. 오류의 상태는 HTTP 상태로도 내려가므로(요구 4) 프록시와 모니터링도 알아본다.
- 컨트롤러는 `ApiResponse<T>`를 반환한다. 상태나 헤더를 바꿔야 할 때(201과 `Location` 등)만 `ResponseEntity`로 감싼다.
- ProblemDetail 표준은 쓰지 않으므로, 표준을 읽는 도구와 라이브러리는 이 응답을 오류로 알아보지 못할 수 있다.
- 클라이언트는 `code`로 분기하고 `status`로 일반 처리를 한다. 오류 코드의 이름을 바꾸면 클라이언트가 깨진다(요구 12).
- 오류 코드가 늘면 `ErrorCode` 한 파일이 길어지고, 여러 사람이 같은 파일을 고쳐 병합 충돌이 날 수 있다. 기능별 묶음과 접두어(요구 10)로 줄인다.
- 업무 오류는 모두 `CustomException`이라서 호출하는 쪽이 오류를 따로 분류하지 않는다.
- Spring MVC의 표준 예외는 부모 클래스(`ResponseEntityExceptionHandler`)가 응답을 만들게 하고 본문만 `ApiResponse`로 바꾸므로, 예외를 하나씩 나열하지 않아도 표준 4xx가 모두 같은 틀로 나간다.
- 공통 코드와 형식을 테스트하려면 표현 계층 테스트에서 오류를 던지는 임시 컨트롤러가 필요하다.
