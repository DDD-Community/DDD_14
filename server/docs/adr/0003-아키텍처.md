# ADR-0003. 아키텍처: 완화된 계층형

- 상태: 제안 (AI가 제안. 팀의 승인 전이다)

읽는 법은 `.claude/skills/work/references/doc-style.md`를 따른다. 굵은 키워드가 없는 문장은 설명이다.

## 맥락

서버의 구조는 완화된 계층형(표현, 응용, 인프라 계층과 가장 안쪽의 도메인 계층)이다. 사용자가 정했다. 요구 1~17번은 AI가 제안했고, 사용자가 2026-11-23에 확인했다. 요구 18~31번은 사용자가 샘플 코드에서 정한 규칙을 2026-11-25에 옮긴 것이다(2026-11-25 일지). 객체지향의 원칙은 도메인 객체가 스스로 일을 처리하는 것이다. 응용 계층은 그 원칙을 해치지 않고, 도메인 객체가 맡기 애매한 일을 맡는다. 응답 DTO의 규칙(13, 14번)은 ADR-0006가 아니라 이 ADR에 둔다.

| 용어 | 뜻 |
|---|---|
| 표현 계층(presentation) | 클라이언트와 상호작용하는 계층. 클라이언트의 요청을 받아 형식을 확인하고, 그 요청을 처리할 응용 계층에 넘기고, 응용 계층이 돌려준 결과를 클라이언트가 요구하는 응답으로 만들어 내려준다 |
| 응용 계층(application) | 도메인 기능(예: 회원가입)의 처리 흐름과 트랜잭션 경계를 가진 계층. 구현 계층이 없으면 도메인 객체에게 직접 일을 시키고 조회와 저장도 맡는다. 구현 계층이 있으면 그 세부를 구현 계층에 맡기고 흐름과 트랜잭션만 가진다. 도메인 객체가 스스로 처리하기 애매한 연산과 조율(DB 접근, 여러 도메인의 조합)을 맡는다 |
| 구현 계층(implement) | 응용 계층의 본문에 흐름만 남기려고, 세부 작업(조회, 검증, 저장, 도메인 객체에게 일 시키기)을 맡는 중간 계층. 트랜잭션 경계는 응용 계층이 가진다. 두는 것은 선택이다 |
| 비즈니스 로직(business logic) | 도메인 기능(예: 회원가입)을 구현하기 위한 규칙과 처리 절차 전체. 규칙은 도메인 객체가 두고, 처리 절차는 응용 계층이 흐름을 정하고 구현 계층이 있으면 세부를 수행한다 |
| 도메인 계층(domain) | 업무 규칙과 상태 변화를 가진 계층. 가장 안쪽이라 모든 계층이 참조한다 |
| 인프라 계층(infrastructure) | DB와 외부 시스템과 실제로 통신하는 계층 |
| 외부 시스템(external system) | 우리 서버 밖의 시스템 (소셜 로그인 제공사, AI 모델 API 등) |

## DDD를 어디까지 따르는가

이 구조는 DDD의 패턴(규칙을 가진 도메인 객체, 애그리거트, 처리 절차를 맡는 응용 계층)을 근간으로 둔다. 완전한 DDD는 아니다. 사용자가 아래 둘을 정했다. 이유는 AI가 설명한다.

| 항목 | 이 프로젝트 | 완전한 DDD | 이유와 비용 |
|---|---|---|---|
| 도메인 모델과 JPA 엔티티 | 나누지 않는다. JPA 엔티티가 도메인 모델이다 | 둘을 나누고 서로 변환한다 | 모델이 하나라서 변환 코드와 중복된 정의가 없다. 작은 팀과 짧은 기간에 코드가 적다. 비용: 도메인 객체가 JPA의 제약(기본 생성자, 지연 로딩, 어노테이션)을 받는다 |
| 도메인 계층의 인프라 인터페이스 | 두지 않는다. 리포지토리는 인프라 계층에 있고 응용 계층이 직접 쓴다 | 도메인 계층에 리포지토리 인터페이스(포트)를 두고 인프라 계층이 구현한다(의존 역전) | 인터페이스와 구현이 짝으로 늘지 않는다(15번의 "겪지 않은 문제"). 비용: 응용 계층이 Spring Data JPA에 묶여 저장 기술을 바꾸기 어렵다. 외부 시스템(AI 모델 API 등)은 구현이 바뀔 가능성이 있어서, 15번에 따라 인터페이스를 둘 수 있다 |

## 결정

요구마다 끝의 대괄호에 지키는 것을 적는다. `[리뷰]`는 검사로 만들지 못한 요구이고 코드 리뷰가 확인한다. 계층의 일은 용어 표가 정의한다. 이 목록은 용어 표에 없는 요구만 적는다.

### 의존 방향

- (1) 의존은 표현 계층에서 응용 계층으로, 응용 계층에서 인프라 계층으로 **반드시** 한 방향으로만 흘러야 한다. 방향을 지키면 계층 하나를 건너뛰어도 된다. 구현 계층을 두면 응용 계층과 인프라 계층 사이에 놓인다. [ArchUnit]
- (2) 도메인 계층은 다른 계층을 **절대** 참조해서는 안 된다. [ArchUnit]
- (3) AI와 사용자는 순환 의존을 **절대** 만들어서는 안 된다. [ArchUnit]
- (4) 응용 계층의 클래스는 다른 응용 계층의 클래스를 **절대** 호출해서는 안 된다. 컨텍스트 사이의 읽기 방식은 아직 정하지 않았다(아래 "정하지 않은 것"). 정하기 전에는 컨텍스트 사이에 응용 계층 호출을 만들지 않는다. [ArchUnit]

4번의 이유(AI가 설명한다):

- 응용 계층의 클래스 하나는 유스케이스 하나다. 이 클래스가 트랜잭션의 경계다. 유스케이스가 다른 유스케이스를 부르면 트랜잭션이 겹치고, 롤백의 범위가 코드에서 보이지 않는다.
- 호출이 서로를 향하면 순환 의존이 쉽게 생긴다(A가 B를 부르고 B가 A를 부른다). 3번은 이것을 막지만, 4번은 순환이 생기기 전에 그 길을 닫는다.
- 컨텍스트(예: 업로드, 퀴즈)의 경계와 통신 방식을 아직 정하지 않았다. 응용 계층끼리의 호출을 열어 두면 그 사이에 임시 호출이 쌓이고, 나중에 방식을 정할 때 고칠 곳이 많아진다.
- 이 요구의 비용: 두 유스케이스가 같은 일을 해야 하면 한쪽이 다른 쪽을 부르지 못한다. 같은 컨텍스트 안의 공통 일은 도메인 객체나 구현 계층으로 내리고, 컨텍스트 사이의 일은 방식을 정한 뒤에 해결한다.

### 계층의 책임

- (5) 표현 계층은 규칙을 **절대** 판단해서는 안 된다. [리뷰]
- (6) 응용 계층은 규칙을 직접 **절대** 두어서는 안 된다. 응용 계층은 흐름과 트랜잭션만 가진다. 규칙은 도메인 객체가 스스로 처리하기 때문이다. [리뷰]
- (7) 인프라 계층은 규칙을 **절대** 판단해서는 안 된다. [리뷰]

5~7번의 이유(AI가 설명한다):

- 규칙이 도메인 객체 한 곳에 있으면 같은 규칙이 여러 곳에 중복되지 않고, 한 곳만 고치면 된다.
- 규칙이 도메인 객체에 있으면 DB와 HTTP 없이 단위 테스트로 규칙을 확인한다.
- 응용 계층에 규칙이 새면 유스케이스마다 규칙이 갈라진다. 표현 계층과 인프라 계층에 규칙이 새면 입출력의 방식(HTTP, DB)을 바꿀 때 규칙이 같이 깨진다.

### DTO와 엔티티

- (8) 표현 계층은 요청 DTO를 응용 계층에 그대로 **절대** 넘겨서는 안 된다. 표현 계층은 값을 꺼내 응용 계층 전용 입력 DTO로 넘긴다. 단순한 식별자는 그대로 넘겨도 된다. [ArchUnit (응용 계층은 표현 계층을 참조하지 않는다)]
- (9) 응용 계층 전용 입력 DTO는 클라이언트의 요청 모양이 아니라 우리가 이해하는 도메인 개념대로 같은 개념의 값을 **반드시** 묶어야 한다. [리뷰]
- (10) 표현 계층은 엔티티의 상태를 바꾸는 메서드를 **절대** 불러서는 안 된다. [리뷰]
- (11) 응용 계층은 엔티티(애그리거트)로 표현하기 어려운 경우가 아니면 엔티티를 **반드시** 반환해야 한다. 어려운 경우의 기준은 정하지 않았고 판단에 맡긴다. [리뷰]
- (12) 응용 계층은 표현 계층이 읽을 값을 모두 **반드시** 읽어 두어야 한다. 표현 계층이 엔티티의 연관 객체를 읽을 일이 없게 하려는 것이다. [리뷰]
- (13) 응답 DTO는 정적 팩토리 메서드 `from(...)` 또는 `of(...)`로 **반드시** 만들어야 한다. [리뷰]
- (14) 정적 팩토리 메서드는 private 빌더를 **반드시** 안에서 써야 한다. [리뷰]

8~14번의 이유(AI가 설명한다):

- 8번과 9번(계층 사이에 DTO를 나눈다): 요청 DTO는 HTTP의 모양(JSON의 필드, 검증 어노테이션)에 묶여 있다. 이 DTO가 응용 계층까지 가면 응용 계층이 HTTP의 변경에 흔들리고, 응용 계층을 HTTP 없이 부르기 어렵다. 입력 DTO로 끊으면 응용 계층은 클라이언트의 모양이 아니라 도메인의 말로 필요한 값만 받는다. 비용: 변환 코드가 늘어난다.
- 9번(도메인 개념대로 값을 묶는다): 표현 계층까지는 클라이언트가 보내는 모양이 기준이다. 응용 계층부터는 클라이언트가 아니라 우리가 이해하는 도메인 개념으로 보여야 읽고 이해하기 쉽다. 같은 개념의 값이 한 객체로 묶이면 매개변수가 늘어서 순서를 헷갈리는 일도 줄어든다.
- 10번: 엔티티의 상태 변경은 응용 계층의 트랜잭션 안에서 일어나야 변경이 DB에 반영되는 경계가 한 곳에서 보인다. 표현 계층이 상태를 바꾸면 그 경계가 흐려진다.
- 11번(엔티티를 반환한다): 응용 계층이 결과용 객체를 따로 만들면 변환이 한 번 더 늘어난다. 엔티티를 돌려주고 표현 계층이 응답 DTO로 바꾸면 변환은 한 번이다. 비용: 표현 계층이 엔티티에 의존한다. 이 비용은 위 표의 "도메인 모델과 JPA 엔티티를 나누지 않는다"와 같은 선택에서 온다.
- 12번(응용 계층이 미리 읽는다): 표현 계층이 연관 객체를 읽으면 그때 DB 조회가 일어나서 어디서 쿼리가 나가는지 코드에서 보이지 않고 N+1이 숨는다. 필요한 값을 응용 계층에서 읽으면 조회가 트랜잭션 안에서 한곳에 모인다.
- 13번과 14번(응답 DTO는 정적 팩토리와 private 빌더로 만든다): 응답의 모양을 한 곳에서 만들어서 필드를 빠뜨리지 않게 하고, 엔티티가 응답으로 그대로 새지 않게 한다. 빌더를 private으로 두면 생성이 팩토리 하나로 모인다.

### 구조를 만드는 기준

- (15) AI와 사용자는 겪지 않은 문제를 풀려고 구조나 추상화(인터페이스, 계층, 클래스 분리)를 **절대** 만들어서는 안 된다. [리뷰]

15번에서 추상화를 만들 이유가 되는 경우: 같은 일을 하는 구현이 둘 이상 있다. 테스트가 구현을 대신하는 대역이 필요하다. 외부 시스템처럼 구현이 바뀔 가능성이 있다. 흐름이 묻힐 만큼 커졌다. 마지막의 기준은 정하지 않았고 판단에 맡긴다. 추상화를 미룰 때는 이유를 일지에 적는다.

15번의 이유(AI가 설명한다): AI는 코드를 쓸 때 인터페이스와 계층을 늘리는 경향이 있다. 늘어난 구조는 읽는 사람과 고치는 사람의 비용이 되고, 겪지 않은 문제를 위한 구조는 대개 맞지 않는다. 그래서 문제를 겪은 뒤에 만들게 한다.

### 설계의 방향

- (16) AI와 사용자는 다른 객체의 상태를 꺼내 밖에서 판단하지 않고, 그 객체가 스스로 판단하게 **반드시** 시켜야 한다. 객체는 스스로 확인하고 거절하거나, 질의 메서드로 답한다. 예: `material.requireExtractable()`, `isUploadedBy`, `exceedsLimit`. 예의 이름은 예시이고, 따닥의 용어는 domain의 용어 표에서 정한다. [리뷰]
- (17) AI와 사용자는 결합도를 낮추고 응집도를 높이는 쪽으로 설계하기를 **권장한다**. 같이 바뀌는 것은 한곳에 모으고, 서로 모르고 지낼 수 있는 것은 서로 모르게 한다. [리뷰]

16번의 이유: 상태를 꺼내 밖에서 판단하면 같은 판단이 여러 곳에 퍼지고, 규칙이 바뀔 때 빠뜨린 곳에서 틀린다. 객체가 스스로 판단하면 6번(규칙은 도메인 객체에 둔다)도 함께 지켜진다. 17번은 방향이라서 위반을 객관적으로 판정하기 어렵다. 그래서 권장 수준으로 두고, 리뷰에서는 같이 바뀌는 코드가 흩어진 경우처럼 구체적인 문제를 지적한다.

### 입력 DTO와 값 객체

- (18) 표현 계층은 개념에 속하는 요청의 값을 필드 수와 관계없이 개념별 입력 DTO로 **반드시** 묶어 넘겨야 한다. [리뷰]
- (19) 표현 계층은 개념의 일부인 식별자를 그 개념의 입력 DTO에 담**을 수 있다**. [해당 없음]
- (20) 경로의 식별자와 본문의 값이 한 개념이면, 요청 DTO의 변환 메서드는 둘을 입력 DTO 하나로 **반드시** 합쳐야 한다. [리뷰]
- (21) 요청 DTO는 값 객체를 **절대** 만들어서는 안 된다. [리뷰]
- (22) 구현 계층이 있으면, 구현 계층은 값 객체를 만들어 애그리거트 루트에 **반드시** 넘겨야 한다. [리뷰]
- (23) 구현 계층이 없으면, 응용 계층은 값 객체를 만들어 애그리거트 루트에 **반드시** 넘겨야 한다. [리뷰]
- (24) 애그리거트 루트는 자기 상태로 계산하는 값 객체를 **반드시** 직접 만들어야 한다. [리뷰]
- (25) AI와 사용자는 도메인 사이에 값 객체를 **절대** 공유해서는 안 된다. [리뷰]
- (26) 도메인은 다른 도메인에서 필요한 값을 값으로만 받아 **반드시** 자기 것으로 가져야 한다. [리뷰]

값의 흐름: 요청 DTO → 입력 DTO(응용 계층) → 응용 계층이 값을 꺼낸다 → 구현 계층이 값 객체를 만든다 → 애그리거트 루트.

| 넘기는 값 | 방법 | 예 |
|---|---|---|
| 개념에 속하는 요청의 값 | 필드가 적어도 개념으로 묶는다 | `NewProductSales(stock, price)` |
| 개념의 일부인 식별자 | 입력 DTO에 담을 수 있다 | `NewOrderItem(productId, quantity)` |
| 개념에 속하지 않는 식별자 | 그대로 넘긴다 (8번) | `memberId` |
| 식별자 하나만 필요한 조회와 취소 | 그대로 넘긴다 (8번) | `findOrder(orderId)` |

표와 번호의 예에 쓴 상품과 주문은 설명을 위한 가짜 예이고 따닥의 도메인이 아니다.

18~26번의 이유(AI가 설명한다):

- 18~20번: 9번의 기준을 정한 것이다. 필드 수로 나누면 필드가 늘 때마다 넘기는 모양이 바뀐다. 개념으로 묶으면 모양이 유지된다.
- 21~23번: 요청 DTO는 입력 DTO까지만 만든다. 구현 계층은 응용 계층의 입력 DTO를 참조하지 않으므로(1번의 방향), 응용 계층이 값을 꺼내 넘긴다. 같은 타입의 매개변수는 순서를 주의한다. 값 객체를 어느 계층이 만드는지는 DDD의 필수 원칙이 아니라 팀의 컨벤션이다.
- 25번과 26번: 판단 기준은 모양이 아니라 개념이다. 필드와 검사가 같아 보여도 뜻과 바뀌는 이유가 다르면 합치지 않는다. 예: 지금 파는 상품 하나의 가격과 주문할 때 확정한 총액은 다른 개념이다. 비용: 비슷한 검사가 두 곳에 생기는 경우가 있다.

### 애그리거트

- (27) 애그리거트는 다른 애그리거트를 연관관계 없이 식별자로만 **반드시** 참조해야 한다. [리뷰 (검사로 바꿀 수 있다)]
- (28) 애그리거트 루트는 다른 애그리거트의 상태를 **절대** 바꿔서는 안 된다. [리뷰]

27번과 28번의 이유(AI가 설명한다): 객체 연관관계가 있으면 한 애그리거트에서 다른 애그리거트의 상태를 바꾸는 길이 열린다. 식별자만 가지면 각 애그리거트를 따로 조회해 바꾸고, 그 조율은 응용 계층이 맡는다. 비용은 아래와 같다.

- JPA가 외래 키 제약을 만들지 않는다. 제약이 필요하면 마이그레이션에 직접 둔다.
- 다른 애그리거트의 값이 응답에 필요하면 따로 조회해 조합한다.

### 현재 시각

- (29) 도메인 객체의 업무 규칙은 현재 시각을 직접 읽지 않고 **반드시** 값으로 받아야 한다. [리뷰 (검사로 바꿀 수 있다)]
- (30) 구현 계층이 있으면, 구현 계층은 도메인 객체에 현재 시각을 **반드시** 넘겨야 한다. [리뷰]
- (31) 한 트랜잭션에서 여러 객체가 같은 시각을 써야 하면, 응용 계층은 시각 하나를 **반드시** 넘겨야 한다. [리뷰]

29~31번은 시각을 누가 넘기는지만 정한다. 구현 계층과 응용 계층이 시각을 얻는 방법(`Clock` 등)은 정하지 않았고, ADR-0004의 E2.1은 그대로 적용한다. 30번과 31번은 DDD의 필수 원칙이 아니라 팀의 컨벤션이다. `BaseEntity`의 생성 시각과 수정 시각은 업무 규칙이 아니라서 29번의 대상이 아니다.

## 정하지 않은 것

| # | 내용 | 어디서 정하나 |
|---|---|---|
| 1 | 컨텍스트의 경계와 컨텍스트 사이의 통신 (이벤트, 조회 인터페이스) | 팀이 ADR로 정한다 |
| 2 | 이름, 로그, 코드 모양 같은 코드의 규칙 | ADR-0006 |
| 3 | 예외의 분류와 오류 응답의 형식 | ADR-0007(오류 응답)이 정한다. `setting/server-init`에 있고 아직 병합 전이다 |

## 버린 대안

| 대안 | 좋은 점 | 버린 이유 |
|---|---|---|
| 헥사고날 (포트와 어댑터) | 경계가 구조로 강제된다 | 포트와 어댑터가 늘어난다 |
| 엄격한 계층형 (계층을 건너뛰지 않음) | 규칙이 단순하다 | 전달만 하는 코드가 늘어난다 |

## 결과

- 규칙이 도메인 객체에 있어서 DB 없이 단위 테스트로 확인할 수 있다.
- 응용 계층의 클래스가 다른 응용 계층의 클래스를 부르지 못해서, 컨텍스트 사이의 읽기 방식은 팀이 ADR로 정한다.
- 표현 계층이 연관 객체를 읽지 않으므로 응용 계층이 필요한 값을 모두 읽는다. 응용 계층의 코드가 길어질 수 있다.
