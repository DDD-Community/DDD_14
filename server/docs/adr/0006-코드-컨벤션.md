# ADR-0006. 코드 컨벤션

- 상태: 제안 (AI가 제안. 팀의 승인 전이다)

읽는 법은 `.claude/skills/work/references/doc-style.md`를 따른다. 굵은 키워드가 없는 문장은 설명이다.

## 맥락

AI가 기본으로는 틀릴 규칙만 이 ADR에 쓴다. 모양에 관한 규칙은 기준 코드와 설정 파일로 넘겼다("코드로 넘긴 규칙"). 구조, DTO, 설계의 방향은 ADR-0003에서 다룬다. 이 ADR은 이름, 로그, 검증, API 문서, 코드 모양을 다룬다. 1.9~1.17와 검증, API 문서의 요구는 사용자가 샘플 코드에서 정한 규칙을 2026-11-25에 옮긴 것이다(2026-11-25 일지).

| 용어 | 뜻 |
|---|---|
| 용어 표 | `docs/domain/`의 용어 표. 이름의 기준이다 |

## 결정

요구마다 끝의 대괄호에 지키는 것을 적는다. `[리뷰]`는 검사로 만들지 못한 요구이고 코드 리뷰가 확인한다.

### 이름

- (1.1) 클래스, 메서드, 변수, 패키지의 이름은 용어 표의 말로 **반드시** 지어야 한다. [리뷰]
- (1.2) 같은 개념에는 이름 하나만 **반드시** 써야 한다. [리뷰]
- (1.3) AI와 사용자는 새 용어를 코드에 쓰기 전에 용어 표에 **반드시** 먼저 적어야 한다. [리뷰]
- (1.4) 코드는 영어로 **반드시** 써야 한다. [리뷰]
- (1.5) 용어 표는 한글 용어와 영어 이름의 대응을 **반드시** 가져야 한다. [리뷰]
- (1.6) 도메인 행위가 있으면 AI와 사용자는 업무에서 하는 말의 이름을 **반드시** 써야 한다. [리뷰]
- (1.7) AI와 사용자는 도메인 행위가 있는 자리에 `setStatus` 같은 데이터를 바꾸는 이름을 **절대** 써서는 안 된다. [리뷰]
- (1.8) AI와 사용자는 행위 이름이 없는 단순한 갱신에 단순한 이름을 쓸 **수 있다**. [해당 없음]
- (1.9) 컨트롤러, `ControllerDocs`, 응용 계층에서 같은 일을 하는 메서드의 이름은 **반드시** 같아야 한다. [리뷰]
- (1.10) 컨트롤러와 응용 계층의 조회 메서드 이름은 `find`로 **반드시** 시작해야 한다. [리뷰]
- (1.11) 구현 계층의 `Reader`의 조회 메서드 이름은 `find`에 업무의 조건이나 목적을 **반드시** 붙여 지어야 한다. 붙일 조건이나 목적이 없는 이름은 `find`다. [리뷰]
- (1.12) AI와 사용자는 삭제되지 않은 것만 찾는 조건을 메서드 이름에 **절대** 적어서는 안 된다. 이 조건은 조회의 기본이다. [리뷰]
- (1.13) AI와 사용자는 인프라 계층의 메서드 이름과 인프라 용어(`ForUpdate`, `WithLock`, `FetchJoin` 등)를 구현 계층의 메서드 이름에 **절대** 써서는 안 된다. 구현 계층의 이름은 업무의 말로 짓는다. [리뷰 (검사로 바꿀 수 있다)]
- (1.14) 생성의 입력 DTO 이름은 `New<개념>`으로 **반드시** 지어야 한다. [리뷰]
- (1.15) 요청 DTO의 이름은 도메인으로 시작하고 동사와 `Request`로 **반드시** 끝나야 한다. 예: `OrderCreateRequest`. [리뷰]
- (1.16) 수정의 입력 DTO 이름은 상황에 맞춰 `Update<개념>`이나 `Modify<개념>`으로 지**을 수 있다**. [해당 없음]
- (1.17) 구현 계층의 메서드 이름은 응용 계층의 메서드 이름과 다르게 지**을 수 있다**. 예: 응용 계층의 `findProduct`, 구현 계층의 `find`. [해당 없음]

### 로그

- (2.1) AI와 사용자는 로그에 비밀값, 토큰, 쿠키 원문, 개인정보를 **절대** 남겨서는 안 된다. [리뷰 (검사로 바꿀 수 있다)]
- (2.2) 로그는 식별자로 대상을 **반드시** 가리켜야 한다. [리뷰]
- (2.3) AI와 사용자는 예외를 던지거나 로그로 남기거나 둘 중 하나만 **반드시** 해야 한다. [리뷰]
- (2.4) 로그는 무슨 일이 있었는지와 맥락(식별자)을 함께 **반드시** 적어야 한다. [리뷰]
- (2.5) 로그의 형식은 `[클래스명] 명사형 설명 - key=value` 하나로 **반드시** 통일해야 한다. [리뷰 (검사로 바꿀 수 있다)]

2.3의 이유: 던지면서 남기고 상위에서 또 남기면 같은 사건이 여러 줄이 된다. 2.5의 예: `[ClassName] 자료 업로드 - materialId=1, userId=2`.

### 검증

원칙: 불변식은 도메인이 지키고, 요청 검증은 같은 규칙을 미리 알려준다. 판단 기준은 "API가 아닌 곳에서 만들어도 이 값이면 안 되는가"다.

- (4.1) 도메인 객체는 API가 아닌 곳에서 만들어도 안 되는 값을 **반드시** 검사해야 한다. [리뷰]
- (4.2) 요청 DTO는 4.1의 값을 도메인과 같은 기준으로 **반드시** 검사해야 한다. [리뷰]
- (4.3) AI와 사용자는 한 API에만 필요한 제한(필수 여부, 입력 형식)을 요청 DTO에만 **반드시** 둬야 한다. [리뷰]
- (4.4) 값 객체는 자기 값의 규칙을 생성자에서 **반드시** 검사해야 한다. [리뷰]
- (4.5) 애그리거트 루트는 직접 가진 값과 자기 불변식을 **반드시** 검사해야 한다. [리뷰]
- (4.6) 도메인 객체는 사용자 입력의 오류를 `CustomException`으로 **반드시** 던져야 한다. [리뷰]
- (4.7) AI와 사용자는 사용자 입력 값의 검사에 `requireNonNull`과 `Assert.hasText`를 **절대** 써서는 안 된다. [리뷰 (검사로 바꿀 수 있다)]
- (4.8) 애그리거트 루트는 받는 값 객체의 `null`을 `requireNonNull`로 **반드시** 막아야 한다. [리뷰]
- (4.9) 검증 오류의 `field` 이름은 요청 필드의 이름과 **반드시** 같아야 한다. [리뷰]
- (4.10) 애그리거트 루트는 직접 가진 값의 검사를 `validate` 메서드 하나에 **반드시** 모아야 한다. [리뷰]
- (4.11) 도메인 객체의 메서드는 검사를 모두 끝낸 다음에 자기 상태를 **반드시** 바꿔야 한다. [리뷰]

4번의 이유(AI가 설명한다):

- 4.1~4.3: 도메인이 검사하면 API가 아닌 곳에서 만들어도 규칙이 지켜진다. 요청 검증은 같은 오류를 더 일찍 알려준다.
- 4.7: 지금 `GlobalExceptionHandler`는 이 두 방법의 예외를 400이 아니라 500으로 응답한다.
- 4.8: 값 객체는 서버의 코드가 만들므로(ADR-0003의 22번과 23번) `null`은 코드의 버그이고 500이 맞다.
- `@Embeddable` record의 compact 생성자에 둔 검사는 DB에서 읽을 때도 실행되는 경우가 있다. 이미 데이터가 있는 컬럼에 검사를 더할 때는 데이터를 먼저 확인한다.

### API 문서

- (5.1) `XxxControllerDocs`는 `@Tag`, `@Operation`, `@Parameter`로 API 설명을 **반드시** 가져야 한다. [리뷰]
- (5.2) 요청 DTO와 응답 DTO는 필드의 설명과 예시를 `@Schema`로 **반드시** 달아야 한다. [리뷰]
- (5.3) `XxxControllerDocs`는 오류 코드와 상태를 `@Operation`의 `description`에 **반드시** 적어야 한다. [리뷰]
- (5.4) AI와 사용자는 컨트롤러에 Swagger 어노테이션을 **절대** 달아서는 안 된다. [리뷰 (검사로 바꿀 수 있다)]

### 코드 모양

엔티티와 DTO의 모양, 포매터의 설정은 초기 셋팅 코드와 설정 파일이 기준이다. "코드로 넘긴 규칙"을 본다.

- (3.1) 엔티티에 업무 상태 필드가 필요하면 `BaseEntity`의 `status`와 다른 이름을 **반드시** 써야 한다. [리뷰]
- (3.2) 도메인 동사가 있으면 팩토리 메서드의 이름은 그 동사로 **반드시** 지어야 한다. 예: `upload`, `split`, `start`. [리뷰]
- (3.3) `var`는 테스트 코드에서만 **반드시** 써야 한다. [리뷰 (검사로 바꿀 수 있다)]
- (3.4) `src/main`은 명시적 타입을 **반드시** 써야 한다. [리뷰 (검사로 바꿀 수 있다)]

객체에게 판단을 시키는 규칙(TDA)과 결합도, 응집도는 ADR-0003의 16번과 17번이다.

## 코드로 넘긴 규칙

아래 규칙은 문장으로 쓰지 않는다. 기준 코드나 설정 파일이 규칙이다. 기준이 되는 것이 먼저 있어야 한다. 그 전까지 규칙은 이 표의 문장이다. 초기 셋팅(첫 슬라이스 전)에서 만들고, 사용자가 확인한다. 기준 코드가 틀리면 AI가 틀린 것을 따라 한다.

| 규칙 | 기준이 되는 것 | 상태 |
|---|---|---|
| C1 `.editorconfig`를 따른다 (4칸 공백, Java 한 줄 120자 이하) | `.editorconfig`와 Spotless 검사(ADR-0002의 요구 12) | 초기 셋팅 전 |
| C2 메서드와 생성자의 선언은 매개변수가 4개 이상이면 길이와 관계없이 한 줄에 하나씩 쓴다. 3개 이하의 선언과 호출 인자는 120자를 넘을 때만 나누고, 나누면 한 줄에 하나씩 쓴다 | Spotless 설정은 120자를 넘는 줄을 나눈다. 개수 기준과 "넘을 때만"은 리뷰가 확인한다 | 초기 셋팅 전 |
| C3 `BaseEntity`는 `status`(`EntityStatus`, 기본 ACTIVE)와 `delete()`, `isDeleted()`를 가진다 | `BaseEntity` 코드 | 초기 셋팅 전 |
| C4 엔티티에 매개변수 있는 생성자를 두지 않는다 | ArchUnit 테스트 | 초기 셋팅 전 |
| C5 엔티티의 기본 생성자는 `protected`다 | ArchUnit 테스트 | 초기 셋팅 전 |
| C6 엔티티는 정적 팩토리 메서드에서 `new`로 만들어 필드를 채운 뒤 돌려준다 | 기준 엔티티 코드 | 초기 셋팅 전 |
| C7 응답 DTO는 레코드이고 `@Builder(access = AccessLevel.PRIVATE)`를 붙인다. 중첩 레코드도 같다 | 기준 응답 DTO 코드 (정적 팩토리 `from`, `of`와 빌더의 쓰임은 ADR-0003의 13번과 14번) | 초기 셋팅 전 |
| C8 record의 컴포넌트는 짧아도 한 줄에 하나씩 쓴다 | Spotless 설정 | 초기 셋팅 전 |
| C9 record 컴포넌트의 어노테이션은 한 줄에 하나씩 쓰고 필드는 그 아랫줄에 쓴다. 어노테이션이 있는 record는 컴포넌트 사이를 한 줄 띄운다 | `build.gradle.kts`의 Spotless 커스텀 단계 | 초기 셋팅 전 |

초기 셋팅 전이라 위 규칙을 **지금 구현하는 사람은 이 표의 규칙을 따른다**. 기준이 만들어지면 이 표에서 상태를 "코드로 대체했다"로 바꾼다.

## 정하지 않은 것

아래는 정하지 않았다. 필요해질 때 정한다.

| # | 내용 | 어디서 정하나 |
|---|---|---|
| 1 | 시각의 형식과 시간대, `Clock` 주입의 방식. 시각을 넘기는 계층은 ADR-0003의 29~31번이 정한다. 시각을 얻는 방법은 테스트 규칙 E2(ADR-0004)의 "시각을 주입받는다"만 있다 | 첫 코드를 쓸 때 (코드가 기준) |
| 2 | 도메인의 null 방어, 도메인 검증의 방식 | 정했다. "결정"의 "검증"(4번) |
| 3 | 로그 레벨의 구분(INFO, WARN, ERROR) | 정하지 않았다 |
| 4 | 주석의 형식 | 정하지 않았다 |
| 5 | `Optional`, 상수 이름, PATCH와 null의 처리, 내부 record의 모양 | 필요해질 때 |
| 6 | 도메인 동사가 없을 때와 값 객체의 팩토리 이름 | 정하지 않았다 |
| 7 | 엔티티의 물리 삭제와 이력 | 해당 기능의 `docs/domain/` |

## 결과

- 시각의 형식과 로그 레벨에는 규칙이 없다. 코드가 기준이 된다.
- 코드로 넘긴 규칙은 기준 코드가 만들어질 때까지 지켜지지 않는다. 초기 셋팅에서 기준 코드를 만들고 사용자가 확인한다.
- 3.3과 3.4, 2.1, 2.5는 검사로 바꿀 수 있다. 같은 교정이 두 번 나오면 검사로 만든다.
