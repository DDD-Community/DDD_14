# Documentation Rule

`docs/` 아래 문서를 작성하거나 이동할 때 반드시 참고해야 하는 규칙이다.
AI coding agent는 문서를 새로 작성하거나 기존 문서를 옮길 때 이 문서의 분류·배치·이름 규칙을 그대로 따른다.

## 최상위 구조

```text
docs/
  rules/
  specs/
  adr/
  plans/
```

> 현재는 `archive/`를 두지 않는다. 과거 문서 보관이 필요해지면 그때 `archive/`를 추가하고 이 규칙에 반영한다.

새 문서를 작성하기 전에 먼저 아래 질문 하나로 최상위 위치를 정한다.

> "이 문서는 규칙인가, 명세인가, 결정인가, 계획인가?"

## 문서 타입 판단 기준

### `rules/` — 규칙

다음에 해당하면 `rules/`에 둔다.

- 여러 작업에서 반복 참조하는 공용 원칙
- 구현 방식의 제약이나 금지 사항
- 특정 영역(예: form, API 호출)에서 공통으로 따라야 할 규칙

예: API 호출 가이드, optimistic update 규칙, form 구현 규칙, 커밋/PR 컨벤션

**파일명 규칙**: 날짜 없이 주제를 직접 드러내는 이름을 사용한다. 예: `api-call.md`

### `specs/` — 명세 (source of truth)

`specs/`는 **현재 코드와 이격이 없어야 하는 source of truth 문서**다. 다음에 해당하면 `specs/`에 둔다.

- 기능 명세, 필드 정의서, API 계약, UI 동작 정의, 기획 상 정책 및 제약
- 아키텍쳐 관련: 컴포넌트 책임, 경계, 흐름, 상호작용 구조 등 (`*-architecture.md`)

예: 세션 관리 구조 설명, 로그인 플로우

**파일명 규칙**: 날짜 없이 주제를 직접 드러내는 이름을 사용한다. 예: `session-management.md`

**spec 최신화 원칙**:

- 관련 작업을 할 때는 항상 관련 spec 문서를 먼저 참조한다.
- 작업으로 인해 spec 내용에 변경이 생기면 반드시 해당 spec 문서를 최신화한다. spec과 코드가 어긋난 채로 방치하지 않는다.
- spec이 **크게 변경**되는 경우(구조가 바뀌거나 기존 방식을 대체하는 경우) 항상 `adr/`에 ADR을 작성하고, spec 문서에 해당 ADR을 참조하는 로그(변경 이력)를 반드시 남긴다.

### `adr/` — 결정

다음에 해당하면 `adr/`에 둔다.

- 장기적으로 유지될 기술 선택
- 여러 모듈에 영향을 주는 구조적 선택
- 대규모 리팩토링
- 왜 특정 대안을 채택하거나 기각했는지 남겨야 하는 경우
- 아키텍처에 한정하지 않고, 코드 구조와 방향성에 영향을 주는 모든 결정 사항

예: 특정 기능에 써드파티 라이브러리를 도입한 결정, spec을 크게 변경하게 된 배경과 대안 비교

**파일명 규칙**: `0001-<주제>.md` 형식으로 고유 번호를 붙인다. 번호는 ADR 작성 순서대로 증가한다. 예: `adr/0001-adopt-state-library.md`

**문서 구조**: `adr/` 문서는 **ADR 표준 구조**를 따른다.

- **제목**: 고유 번호와 직관적인 주제를 명시한다.
- **상태 (Status)**: 제안됨(Proposed) / 수락됨(Accepted) / 거절됨(Rejected) / 보류됨(Deferred) / 대체됨(Superseded) 중 현재 처리 단계를 명시한다.
- **배경 (Context)**: 이 결정을 내리게 된 기술적/비즈니스적 원인과 해결하려는 문제를 설명한다.
- **결정 (Decision)**: 채택한 방식을 명확히 밝히고, 이유와 고려했던 대안(장단점 포함)을 기록한다.
- **결과 (Consequences)**: 이 결정이 시스템/팀에 미칠 긍정적/부정적 영향과 트레이드오프를 서술한다.

작성 원칙:

- 과거 결정을 덮어쓰지 않는다. 결정이 변경되면 원본 문서의 상태를 `Superseded`로 업데이트하고, 새 ADR 문서를 작성해 변경 이력을 추적한다. 새 문서에는 대체 대상 ADR을 참조한다.
- 코드가 아닌 **의사결정의 맥락**에 집중하여 간결하게 작성한다.

### `plans/` — 계획

다음에 해당하면 `plans/`에 둔다.

- 아직 구현 전이거나 진행 중인 작업 계획
- AI가 작성한 리팩터링 초안
- 단계별 이행 순서를 담은 문서

예: 로그인 기능 구현 계획, 기능 리팩토링 절차 초안

**주의**: 내용이 실제로 미확정 실행 계획이라면 파일명에 `plan`이 없어도 `plans`로 분류한다. plan이 규칙인 것처럼 소비되어 잘못된 구현 방향을 유도하지 않도록 주의한다.

**파일명 규칙**: 날짜 접두어를 유지한다. 예: `2026-07-14-docs-reorganization-plan.md`

**문서 형식**: 아래 템플릿을 따른다. 상단의 `- 상태: 진행 중` 줄은 에이전트 훅이 진행 중인 plan을 찾는 데 쓰므로 형식을 바꾸지 않는다.

```md
# <작업 이름>

- 상태: 진행 중
- 담당:
- 관련: spec / adr / 이슈 링크

## 목표

## 범위 밖

## 단계

- [ ] 1.

## 검증 방법

## 진행 로그

- YYYY-MM-DD:
```

**수명주기**: 진행하면서 단계 체크리스트와 진행 로그를 갱신한다. 작업을 마무리하는 PR에서 plan을 삭제한다(보관은 git 이력이 맡는다). 남겨야 할 내용은 삭제하기 전에 `specs/`·`adr/`로 옮긴다. 그래서 `plans/`에 남아 있는 문서는 모두 진행 중인 작업이다.

## 문서 작성 시 체크리스트

새 문서를 작성하거나 이동할 때 다음 순서로 판단한다.

1. 이 문서는 규칙/명세/결정/계획 중 무엇인가 → 최상위 폴더 결정
2. plan 문서인데 실제로는 명세/결정에 가까운 내용은 없는가 → 있다면 재분류한다

## spec 작업 시 체크리스트

`specs/`에 있는 문서를 참조하거나 수정하게 되는 작업을 할 때는 다음을 반드시 지킨다.

1. 관련 작업을 시작하기 전에 해당 spec 문서를 먼저 읽는다.
2. 작업 결과로 spec의 내용(동작, 필드, 계약, 구조)이 바뀌었다면, 코드 변경과 함께 spec 문서도 최신화한다. spec과 코드가 어긋난 상태로 두지 않는다.
3. 변경이 **구조를 바꾸거나 기존 방식을 대체할 만큼 크다면**:
   - `adr/`에 ADR을 새로 작성한다.
   - 수정한 spec 문서에 해당 ADR을 참조하는 변경 로그를 남긴다.

## AI coding agent의 탐색 순서

구현 작업 전 문서를 참조할 때는 다음 우선순위로 좁혀 읽는다.

1. `rules/` — 반드시 지켜야 할 제약이 있는가
2. `specs/` — 구현 대상의 source of truth 명세가 있는가
3. `adr/` — 과거에 이미 결정된 사항이 있는가, 특히 spec이 왜 지금 형태로 바뀌었는가
4. `plans/` — 아직 확정되지 않은 진행 중 계획은 무엇인가

`plans/` 문서는 실행 전이거나 진행 중인 초안이므로, 확정된 규칙(`rules/`)이나 결정(`adr/`)과 동일한 권위로 취급하지 않는다. `specs/` 문서를 읽을 때는 항상 현재 코드와 일치하는 것을 전제로 신뢰하되, 최근에 관련 작업이 있었다면 실제 코드와 대조해 이격이 없는지 확인한다.
